# ISR + Redis / 搜索缓存体系 Deep Dive

> 目的：把 joyboy **服务端 ISR/Redis 全站缓存** 与 **搜索客户端 responsesCache** 两套独立系统讲清楚，并配上面试向 Q&A。所有结论均可在源码路径中验证。
>
> **先记住一句话**：Redis 管的是 Next.js 的 Full Route Cache / Data Cache（跨 Pod 共享）；搜索的「两层去重」管的是浏览器内存里的 InstantSearch 请求（不进 Redis）。

---

## 0. 两套系统对照（先别混）

| 维度 | ISR + Redis（Next.js Cache Handler） | 搜索 responsesCache |
| ---- | ------------------------------------ | ------------------- |
| 位置 | `apps/web/cache-handler.js` + `next.config.js` | `libs/modules/search/components/.../search-client.ts` |
| 运行时 | Node 服务端（生产） | 主要是浏览器；SSR 也有一份 ephemeral |
| 存储 | Redis（失败时进程内 LRU） | 进程/页签内存 `Map` |
| 缓存什么 | 页面 HTML、`fetch`/`unstable_cache` 结果 | InstantSearch 的 `search()` 响应 Promise |
| 典型 TTL | 页面 `revalidate=600`；Redis expire 估算 **3600s** | 结果 **2 分钟** |
| 超时 | Redis 操作 **`timeoutMs: 1000`** | 单次搜索请求 **10s** |
| PLP/Search 是否走 ISR？ | **否**——PLP 路由是 `force-dynamic` | **是**——客户端去重 + SSR hydrate |

旧文档 [`docs/search-result-cache.md`](./search-result-cache.md) 描述的是更早一版（独立 Result Map + Pending Map、5 分钟 TTL、`clearSearchResultCache`）。**以本文 + `search-client.ts` 为准。**

---

## 1. ISR + Redis：服务端全站缓存

### 1.1 它解决什么问题

多 Pod / 多实例部署时，Next.js 默认的内存 Full Route Cache **不跨进程共享**。生产环境通过自定义 `cacheHandler` 把缓存落到 Redis，使：

- Pod A 生成的 ISR 页面，Pod B 可直接命中；
- `unstable_cache` / `fetch` 的 Data Cache 也可跨实例共享；
- Redis 挂了或超时 → 降级为进程内 LRU，站点仍可用（只是缓存不共享）。

### 1.2 接入点

**`apps/web/next.config.js`**

```js
cacheHandler: process.env.NODE_ENV === 'production' ? require.resolve('./cache-handler.js') : undefined,
cacheMaxMemorySize: 0, // 禁用 Next 默认内存缓存，避免与自定义 handler 双写
```

- **仅 production** 启用 Redis handler；本地 / CI 不走 Redis。
- `cacheMaxMemorySize: 0` 关掉默认内存层，避免「本地一份、Redis 一份」语义混乱。

**`apps/web/cache-handler.js`**（核心逻辑摘要）

```js
handler = await createRedisHandler({
  client,
  keyPrefix: `${process.env.APPLICATION_ENV}-${buildId}:`,
  timeoutMs: 1000,
});

return {
  handlers: [handler],
  ttl: {
    estimateExpireAge: (staleAge) => 3600,
  },
};
```

要点：

1. **库**：`@neshca/cache-handler` + `redis-strings` handler（纯 Redis string，无 RedisJSON/Search 依赖）。
2. **连接**：生产读 `REDIS_URL`；连接失败则 `createLruHandler()` 兜底。
3. **key 前缀**：`${APPLICATION_ENV}-${buildId}:` —— 环境隔离 + **发版后旧 build 的缓存自然失效**（新 buildId 写新命名空间）。
4. **`timeoutMs: 1000`**：单次 Redis get/set 等操作最多等 1 秒（见 §3 Q1）。
5. **`estimateExpireAge → 3600`**：把写入 Redis 的物理过期时间估成 **1 小时**（见 §3 Q2）。

### 1.3 ISR 在业务页面上的用法

内容型页面普遍：

```ts
export const revalidate = 600; // 10 分钟
```

出现在 home / blog / help-center / contact-us / `[...rest]` CMS 页 / TandC 等。

配合 Storyblok Data Cache：

```ts
// libs/config：默认 600 秒
NEXT_PUBLIC_STORYBLOK_REVALIDATE_TIME || 600

// sbBaseService / storyblok fetch 里
unstable_cache(fn, [cacheKey], {
  tags: ['storyblok', ...],
  revalidate: options?.revalidate || EcEnv.NEXT_PUBLIC_STORYBLOK_REVALIDATE_TIME,
})
```

按需失效：`apps/web/app/api/storyblok/route.ts` 里对 webhook 调 `revalidateTag` / `revalidatePath`。

ISR 语义回顾（Next App Router）：

1. 首次请求（或 build 的 `generateStaticParams`）生成页面并缓存；
2. `revalidate` 窗口内后续请求吃缓存（可来自 Redis）；
3. 过期后：**先返回 stale，再后台再生**（stale-while-revalidate 风格）；
4. Tag/Path 主动失效可立刻丢掉对应条目。

### 1.4 PLP / Search **不走** ISR

```ts
// apps/web/app/.../(PLP)/search/page.tsx
// categories / collections / sales 同理
export const dynamic = 'force-dynamic';
```

原因：列表依赖 query / facet / 个性化与实时库存语义，不能用「整页静态 HTML + 10 分钟 ISR」兜住。PLP 性能靠：

- SSR 首屏搜一次 + InstantSearch hydrate；
- 客户端 `responsesCache` 去重重复 `search()`；
- 后端搜索服务自身的缓存（若有，不在本文范围）。

架构文档里写的「PLP = SSR/ISR」是粗粒度说法；**路由层事实是 `force-dynamic`。**

### 1.5 数据流（ISR 页）

```
Browser
  → Next.js Pod
      → cacheHandler.get(key)
          → Redis (timeout 1s) ──命中──→ 返回缓存 HTML / Data
          → miss / timeout / Redis down
              → 渲染 / fetch / unstable_cache
              → cacheHandler.set → Redis (expire ~3600s)
```

`instrumentation.js` 里 `registerInitialCache` **目前是注释掉的**——启动时不会主动把 build 产物灌进 Redis；靠真实流量逐步回填。

## 2. 搜索缓存：`createResponsesCache`

### 2.1 它解决什么问题

自定义 `searchClient` 不是官方 Algolia client。若不实现 Algolia v4 的 `transporter.responsesCache` 契约：

1. **Hydration 后必搜一次**：`InstantSearch.start()` → widget 注册 → `scheduleSearch`；官方会用 SSR 结果预填缓存，第三方 client 会被 skip → 多一次 `POST /api/search` → `CustomHits` 进 loading → **闪烁**。
2. **Facet 点一次发两次 POST**：`react-instantsearch-nextjs` 的 routing bridge 会在 `pushState` 后再 `setUiState` → 第二次与第一次参数相同。

详见：[`docs/issues/records/2026-07-17-plp-search-flicker-redundant-request.md`](./issues/records/2026-07-17-plp-search-flicker-redundant-request.md)。

### 2.2 「两层」到底是什么

面试里常说的「搜索两层」在本项目对应 **同一套 Map 上的两种去重语义**（不是两个独立 Redis）：

```
search(requests)
  → responsesCache.get(key, fallback)
       ├─ 未过期 entry 存在
       │     └─ 直接 return 同一个 Promise
       │           ├─ 已 resolve → 结果 TTL 命中（结果复用）
       │           └─ 仍 pending → in-flight 命中（并发去重）
       └─ miss / 过期
             → 跑 fallback（真网络）
             → 立刻把「进行中的 Promise」写进 Map（带 expiresAt）
             → 成功保留；失败 / artificial 驱逐
```

| 「层」 | 机制 | 作用 |
| ------ | ---- | ---- |
| **结果 TTL** | `expiresAt = now + 2min`，存的是已 settle 的 Promise | 后退、重复相同 query、routing 二次 search → 不打网 |
| **in-flight Promise** | miss 时先 `entries.set(key, { value: promise })` 再等网络 | 并发相同 key 共享一次 `fallback` |

旧实现把「结果 Map」和「pending Map」拆开；现实现 **缓存 Promise 本身**，一层结构覆盖两种场景（见源码注释 L142–146）。

另有一个 **运行时上的双 wrap**（hydrated 页面）：

1. **外层**：`hydrateSearchClient` override 的 `search`，key = 库自己的 `serializeQueryParameters`；
2. **内层**：我们 `createSearchClient` 里对 `search` 的 wrap，key = `stableStringify({ method, args: [requests] })`。

两层 key 故意不同，避免「外层 fallback 读到自己刚写入的 in-flight」死循环式命中（见 `createSearchClient` 注释）。

### 2.3 关键常量（以代码为准）

| 常量 | 值 | 含义 |
| ---- | -- | ---- |
| `RESPONSES_CACHE_TTL_MS` | `2 * 60 * 1000`（2 分钟） | 相同序列化请求的结果 / in-flight 共享窗口 |
| `RESPONSES_CACHE_MAX_ENTRIES` | `100` | FIFO 按插入序驱逐 |
| `SEARCH_REQUEST_TIMEOUT_MS` | `10_000`（10 秒） | 单次 `fetch` AbortController 超时 |

### 2.4 Key 与特殊规则

- Key：`stableStringify({ method, args })`，对象 key 排序；`params` 里 **`page=0` 会删掉**（SSR 常省略 page，hydration 会带 `page=0`，必须视为同一请求）。
- **Artificial empty**（降级空结果）：可返回给当前调用者，但 **不留在缓存**，避免污染后续请求。
- **fallback reject**：从 Map 删除，下次相同 key 会重试，不会永久记住失败。
- `clearCache()`：InstantSearch `refresh()` / Retry 会清掉整表。

### 2.5 SSR vs Client 错误策略

| 环境 | 失败时 | 原因 |
| ---- | ------ | ---- |
| Client | **reject**（带 `userMessage`） | 对齐官方 Algolia，框架进 `status='error'`，Toast 可重试 |
| Server | **resolve** artificial empty | `InitializePromise` 只听 `'result'`，reject 会挂死 RSC |

请求超时 10s：用户文案 *Search is taking longer than expected...*；timeout / network / 5xx **不在 client 重复报 Sentry**（服务端 route 已报）。

### 2.6 与 Redis 的关系

**没有关系。** 搜索结果不写 `cache-handler` / Redis。语义搜索设计文档里的 embedding Redis 是另一条规划线（独立 client + `embedding:` 前缀），与本 PLP responsesCache 无关。

## 3. 面试核心问答

### Q1. Redis `timeoutMs` 是多久？为什么？

**答：1000ms（1 秒）。**

它是 **单次 Redis 操作的超时**，不是缓存 TTL，也不是页面 `revalidate`。

为什么压到 1s（库默认往往是 5s）：

1. Cache handler 挂在渲染 / Data Cache 读路径上——Redis 慢或半开着时，若干等几秒，**TTFB 直接被拖死**。
2. 超时后操作视为失败，可走 miss 路径重新生成或落到 LRU 兜底；**宁可少命中，不可整页挂起**。
3. AWS ElastiCache 同 region 正常 RTT 远小于 1s；1s 足够区分「偶发慢」与「不可用」。

对比：启动时 `client.connect()` 注释写明 **没有超时**（会阻塞进程起来）——那是启动路径；运行期读写必须有 `timeoutMs`。

### Q2. Redis 里条目实际过期多久？和 `revalidate = 600` 什么关系？

**答：物理 expire 通过 `estimateExpireAge: () => 3600` 估成约 1 小时；逻辑新鲜度由页面 / `unstable_cache` 的 `revalidate`（常见 600s）决定。**

- `revalidate = 600`：Next 认为 10 分钟后内容 **stale**，可触发后台再生。
- `estimateExpireAge`：告诉 neshca **Redis key 何时删掉**。项目写成恒定 `3600`，避免 key 永不过期占满 Redis；也比「仅 600s」多留一点 stale 窗口给 SWR。
- Tag 主动 `revalidateTag` 仍可立即失效，不靠等到 3600。

### Q3. 搜索「两层」是什么？

**答（推荐口径）：同一 `responsesCache` 上的「结果 TTL 复用」+「in-flight Promise 合并」。**

- 结果 TTL：2 分钟内相同 key 直接复用已完成响应。
- in-flight：请求尚未返回时，后到的相同 `get` 挂到同一个 Promise，只打一次网。

补充：hydrated PLP 上还有 hydrate 外层 override + 我们内层 wrap 的双 key 空间，但面试优先讲「Promise + TTL」这一层业务语义。

### Q4. in-flight promise + 结果 TTL 去重是怎么实现的？

**答：`Map<string, { value: Promise; expiresAt; isArtificial }>`。**

```ts
get(key, fallback) {
  const hit = entries.get(serialized);
  if (hit && hit.expiresAt > Date.now()) return hit.value; // 含未完成 Promise

  const result = Promise.resolve(fallback())
    .then(...)
    .catch((e) => { entries.delete(serialized); throw e; });

  entries.set(serialized, { value: result, expiresAt: Date.now() + TTL, ... });
  return result;
}
```

关键设计选择：

- 存 **Promise** 而不是「pending 另表 + result 另表」→ 并发与串行去重统一；
- 先 set 再 await → 第二个并发 get 一定能 join；
- 失败驱逐 → 不缓存毒结果；
- artificial 驱逐 → SSR/降级空结果不污染交互后的真搜。

单测钉死：`shares one in-flight request between concurrent identical gets`、`does not serve a failed fallback to a later identical call`（`search-client.spec.ts`）。

### Q5. 为什么搜索 TTL 是 2 分钟而不是 5 分钟？

**答：当前代码是 2 分钟（`RESPONSES_CACHE_TTL_MS`）。** 旧文档写 5 分钟已过时。

2 分钟的权衡：

- 够盖住「点 facet → routing 二次 search」「短时后退」；
- PLP 价格/库存变化相对快，过长 TTL 易展示陈旧 hits；
- 缓存 key 含完整 filter/page/query——交互改条件必 miss，TTL 只保护 **完全相同** 的请求。

### Q6. 为什么 PLP 不用 Redis / ISR？

**答：路由显式 `force-dynamic`。**

列表页 URL/facet 组合爆炸、且要跟搜索后端实时性对齐；把整页 HTML 丢进 Redis ISR 收益差、失效复杂。性能拆在：SSR 一次搜索 + 客户端 responsesCache +（可选）搜索后端缓存。

### Q7. `keyPrefix` 为什么带 `buildId`？

**答：发版隔离。** 新部署 `buildId` 变了，读写都在新前缀下；旧 key 靠 Redis TTL（~3600s）自然淘汰，避免新代码读到旧构建序列化形态的缓存导致诡异 bug。

### Q8. Redis 挂了用户会怎样？

**答：handler 创建失败 → `createLruHandler()`；运行中操作超时 → 当次当 miss。** 页面仍能 SSR/再生，只是：

- 多 Pod 之间不再共享缓存；
- 同源流量更容易打到源站 / Storyblok。

生产应监控 Redis 错误（`NEXT_PRIVATE_DEBUG_CACHE=1` 才打详细 Redis error 日志，避免刷屏）。

### Q9. 自定义 searchClient 为什么必须暴露 `transporter.responsesCache`？

**答：让 `hydrateSearchClient` 认作 Algolia v4 client。** 否则跳过预填 → hydration 强制二次网络搜索 → 命中区被骨架替换 → 闪烁。我们只实现最小 `get`/`set`/`clear`，key 序列化仍交给 InstantSearch，避免与库分叉。

### Q10. `credentials: 'omit'` 和搜索缓存有关吗？

**答：有关安全边界，无关 Redis。** `customFetch` 明确不带 cookie；搜索鉴权/个性化不走浏览器 Cookie 自动携带。缓存的是「请求体序列化后的响应」，不含用户 Cookie 整包，降低把登录态结果写进共享结构的风险（responsesCache 本身也只在内存、不跨用户进程共享）。

### Q11. `cacheMaxMemorySize: 0` 为什么要关？

**答：生产已用自定义 cacheHandler 时，关掉 Next 默认内存 Full Route Cache，避免双层缓存行为不一致、内存重复占用，并强制共享路径走 Redis（或我们配置的 LRU fallback）。**

### Q12. Storyblok webhook 失效和 Redis TTL 谁优先？

**答：主动 `revalidateTag` / `revalidatePath` 优先。** TTL / `estimateExpireAge` 是兜底；内容发布应走 webhook，而不是干等 600s 或 3600s。

### Q13. 搜索超时 10s 和 Redis timeout 1s 为什么差这么多？

**答：保护的对象不同。**

| 超时 | 保护 |
| ---- | ---- |
| Redis 1s | 缓存旁路读——失败应立刻回源渲染 |
| Search 10s | 主业务查询（ES 等）——正常 <1s，10s 是挂死兜底 |

不能把搜索超时也裁成 1s：偶发慢查询会大量误杀。

### Q14. 如何验证搜索去重生效？

**答：**

1. 首屏：Network 里 hydration 后不应再多一次与 SSR 相同的 `POST /api/search`。
2. 点一个 facet：通常 **1 个** POST（body 内可有多个 sub-request），不应出现两个 body 完全相同的独立 POST。
3. 跑 `pnpm nx test modules-search-components --testFile=.../search-client.spec.ts`（以实际 project 名为准）。

## 6. 一句话收束

**Redis + ISR** 让多实例 Next **共享页面与 Data Cache**，并用 **1s 操作超时 + ~1h Redis TTL + 600s revalidate** 在可用性与新鲜度之间折中；**搜索两层**是浏览器里 **「TTL 结果复用 + in-flight Promise 合并」**，专门消灭 InstantSearch hydration / routing 的重复请求——二者不要在面试里讲成同一套缓存。
