**我们做的不是“接几个埋点 SDK”，而是建立一套“可观测、可分流、可合规”的前端数据采集体系。**

也就是三层：

- `埋点` 解决“发生了什么”
- `Feature Flag / Experiment` 解决“为什么不同用户看到不同东西”
- `隐私合规` 解决“哪些数据在什么条件下可以采”

---

**1. 埋点：你们项目里最重要的不是 SDK，而是事件设计**

先说结论，你们项目里的埋点设计已经不是单一 GA 那种“哪里点了就发一个事件”，而是更像一个统一事件总线。

最典型的例子是 `Add to Cart`。  
它不是只发一个 GA event，而是一次业务动作成功后，统一触发多个系统：

- GA
- Facebook CAPI
- Pinterest
- DY
- Klaviyo

也就是说，在你们项目里，**埋点的单位不是“某个平台事件”，而是“某个业务动作的统一观测出口”**。

这个设计很重要，因为它解决了两个常见问题：

1. 不同平台各写一套逻辑，后面改一个业务动作要改很多地方
2. 不同平台事件口径不一致，最后数据对不上

所以你面试里可以先讲一句：

**我们不是按埋点平台组织代码，而是按业务动作组织埋点。**

比如：

- 商品曝光
- 商品点击
- Add to Cart
- Checkout
- Purchase

每个业务动作再向多个分析平台分发。

**这个总线在工程上是怎么实现的（追问准备）：**

是一条严格的单向事件流，四层解耦：

```
UI 组件 / services command
  → dispatch domain 语义事件（createAction，比如 promotion/appliedCouponActionSucceeded）
  → tracking 模块的 listener（Redux listener middleware）订阅
  → 扇出到各渠道 trigger（createAsyncThunk：校验 → 组装 payload → 调 SDK）
  → GA / DY / Klaviyo / FB CAPI / Pinterest CAPI / UTT
```

三个关键约束，每个都能展开：

1. **Co-location**：事件定义在 owning 业务模块（cart 的事件放 cart/domain），不放 tracking 模块——埋点语义归业务域所有；
2. **payload 自带全部上下文**：listener 和 trigger 里禁止读 store、读 window、读 pathname 反查字段。比如 shipping zipcode selector 横跨 PDP/搜索/购物车/结算四个入口，`source` 字段是 UI dispatch 时显式带的，不是 trigger 猜的；
3. **listener 不直接 import trigger**：统一走 `events/{channel}.events.ts` 的常量桶（`EVENT_GA_CHECKOUT` 这种别名），扇出列表就是纯数据，可以整体 `Promise.allSettled` 并发且互不阻塞。

业务侧不知道渠道存在，渠道侧不知道业务存在——中间靠事件契约（TypeScript schema）解耦。

---

**2. 你们埋点设计里一个很好的点：服务端补上下文，客户端只负责触发**

这个点特别值得讲。

像 DY 的 PLP Ranking click，你们不是前端点击时临时拼一堆 tracking 参数，而是服务端在返回商品列表时，就把 `decisionId`、`variationId`、`slotId` 这些实验/推荐上下文附着到商品数据上。

然后客户端点击产品卡片时，只需要读取产品身上的 tracking metadata，再统一触发 engagement 上报。

这个设计的价值是：

- 埋点上下文更准确
- 前端组件不需要知道实验平台的复杂细节
- SSR 排序结果和客户端点击结果能对得上

面试里这个特别加分，因为它体现出你理解：

**埋点不是“点击后发请求”这么简单，关键是上下文从哪来、怎么保证不丢。**

这个思路和事件流的 "payload 自带上下文" 原则是同构的：上下文在产生的地方附着，不在消费的地方反查。

---

**3. 面试里说埋点，最关键的不是“发了哪些事件”，而是“怎么保证数据质量”**

这是最重要的面试点。

你可以从 4 个角度讲：

1. **统一事件入口**

避免每个页面自己乱调 SDK，减少重复和漏埋。GA 侧全站只有一个 dataLayer 写口（`gaTrack`），UI 手写 `_event: 'trackEvent'` payload 在代码里已经清零。

2. **事件和业务动作对齐**

比如 Add to Cart 必须在真正加入购物车成功后再触发，而不是按钮点击就发。工程上是用 services 层 command 保证的：UI dispatch 一个 command thunk，command 在 mutation 成功后才 dispatch 语义事件——时机由 services 保证，不由组件自觉。

3. **埋点不能阻塞主流程**

你们很多 tracking thunk 里都体现了这一点，失败只记日志，不影响下单、加购、支付。多渠道扇出统一 `Promise.allSettled`——一个渠道挂了不影响其他渠道，更不影响业务；CAPI 请求带 `keepalive`，页面卸载也不中断。

4. **埋点上下文要前后一致**

比如用户身份、页面来源、实验 variant、产品信息，最好在统一层补齐，而不是页面自己拼。

**追问“具体有什么机制保证质量”时，有三个硬核例子：**

- **GA 的 dataLayer 是 append-only**：上一个事件的 `transactionId` 会残留串到下一个事件。所以 `gaTrack` 每次 push 事件前先 push 一个 reset 信封清掉脏字段，pageview 前再额外重置 21 个页面级字段；
- **event_id 跨渠道去重**：purchase 的 eventId 在 listener 层生成一次，同一个 ID 同时给 FB 和 Pinterest——FB 靠它做 pixel 和 CAPI 的服务端去重，跨平台数据对得上；订单级幂等再用 Set 按 orderId 兜底；
- **schema 即契约**：每个渠道一份 TS schema 文件（trigger 入参 + 渠道出参），checkout 漏斗用 `step: 1|2|3|4|5` 判别联合收窄 payload，编译期就挡住字段错配，trigger 里再加运行时校验兜底。

你可以直接记一句很适合面试的话：

**埋点系统最难的不是接 SDK，而是控制事件口径、上下文一致性和主流程隔离。**

---

**4. Feature Flag / Experiment：你们做的不是“开关配置”，而是按市场、按实验做分流治理**

你们这块有两个比较典型的特点。

第一，**feature 不是全局一刀切，而是按市场拆分**。  
tracking 域自己就有每市场一份的 feature 常量（`features/us.ts`、`sg.ts`…），像 `enabledFacebookCapiV2` 这种开关控制 FB CAPI 从 V1 到 V2 的迁移节奏——不同市场可以不同步。这说明你们的 feature flag 不只是“功能开关”，更是多市场运营策略的一部分。

第二，**experiment 有单独的实验埋点语义**。  
比如 PLA layout experiment，你们不是只切 UI，还会记录：

- 实验 ID
- variant
- 曝光事件
- feature flag response

这说明实验体系不是“把用户随机分组”就结束了，而是要确保实验分流和实验数据采集是打通的。

所以你面试里可以说：

**Feature Flag 在我们项目里有两层价值，一层是安全发布，一层是实验分流。**

安全发布的意思是：

- 某些能力先灰度给部分市场
- 某些第三方追踪先按市场开启
- 某些新功能可以随时关闭回滚

实验分流的意思是：

- 同一页面给不同 variant
- 同时记录用户落入哪个实验组
- 后续才能和转化、点击、曝光关联分析

**追问“埋点本身也受 flag 控制吗？”——是，两个层次：**

- 渠道级：UTT（impact.com）的集成深度按市场分层——CA/UK 全量前端加载，AU/SG/US 的 loader/consent/identify 由 GTM 负责、前端只发 conversion，这背后是 flag + 市场判断的三重 gate；
- 事件级：新链路事件（如 cart 迁移后的 tracking listeners）挂在 `enabledOrderV2` 上，旧链路没验证完之前新事件不上。

**5. 面试官如果追问：Feature Flag 和普通配置有什么区别**

你可以这样回答：

**普通配置是静态的，Feature Flag 是可运营、可灰度、可快速回滚的运行时控制。**

在实际工程里，它的价值主要有三个：

1. 降低上线风险
2. 支持灰度和实验
3. 避免为了一点开关改动重新发版

如果再结合你们项目讲，就可以补一句：

**尤其在 tracking 和实验场景下，flag 的意义不只是控制 UI，还控制“哪些事件该发、哪些能力该开”。**

（关于 flag 体系本身的完整面试口径——三层模型、构建期静态求值、无百分比灰度——见 `2.平台架构+i18n.md` 的 Feature Flag 章节。）

**6. 隐私合规：你们这块最成熟的点，是把 consent 前置成了系统闸门**

这块你一定要讲“闸门”这个词。

你们不是“先把脚本都加载了，再决定要不要用数据”，而是更前一步：

**没有 consent，就不让对应脚本下载和执行。**

这里的核心工具思路是：

- 用 CookieYes 管 consent banner
- 按类别区分 consent：necessary / analytics / advertisement / functional 等
- 第三方脚本通过 `CookieYesScriptGate` 阻断
- React 组件通过 `useConsent` 控制渲染
- 再把 consent 映射到 Google Consent Mode

**闸门在链路上的三个具体位置（追问准备）：**

1. **脚本加载前**：GTM 加载时先 push `gtag('consent','default',...)`（按市场给默认同意态，欧盟市场默认全拒），再加载 GTM 本体；
2. **事件发送前**：FB/Pinterest CAPI 的发送函数里先过 `checkConsentGranted(['advertisement','analytics'])`，没同意就静默跳过——不是报错，是不发；
3. **组件渲染前**：UTT 的 `ConsentBridge` 组件专门把 CookieYes 同意态桥接成 UTT 的 consent 事件，登录用户则由 `IdentifyBridge` 桥接。

这意味着隐私不是页面层的 if 判断，而是平台能力。

这个设计特别适合面试，因为它能体现你们不是“补合规”，而是把合规做进基础设施。

---

**7. 隐私这块最应该讲的面试点，不是 GDPR 名词，而是工程落地方式**

你重点记这三个点：

1. **脚本阻断优先于事件阻断**

最稳的方式不是“脚本执行了但不发事件”，而是根本不让脚本先跑起来。

2. **不同类别分开控制**

analytics 和 advertisement 不应该混在一起，因为合规要求和业务用途不一样。CAPI 的 consent 检查就是 `advertisement` 和 `analytics` 两类都要求。

3. **同意状态要能映射到各个平台协议**

比如 Google Consent Mode，不是只存一个 yes/no，而是要翻译成 `ad_storage`、`analytics_storage` 这些标准字段。

**再加一个 PII 处理的实例，很加分：**

CAPI 的 `user_data` 是 SHA-256 哈希后才上传的（FB V2 和 Pinterest 在前端就哈希，FB V1 由后端哈希）；UTT 的 identify 用 SHA-256(email)，而且代码里刻意不把任何用户标识写进日志和 Sentry——埋点体系和可观测体系都有 PII 边界意识。

面试里你可以说：

**隐私合规如果只停留在 banner 展示层，其实是假的；真正有效的是把 consent 接到脚本加载、组件渲染和事件发送链路上。**

**8. 你们项目里一个很真实的坑，也很适合面试讲**

你们有个 GTM consent 相关问题，本质上不是“埋点没发出去”，而是：

**consent 初始化脚本本身写坏了，导致脚本语法错误，进而影响追踪和合规状态。**

这个 case 很适合面试，因为它说明：

- tracking/consent 脚本虽然不影响主交易链路
- 但它会影响数据准确性和合规状态
- 所以这类代码也需要严肃治理，而不是当“边缘脚本”看待

你不需要讲太细，但可以提一句：

**我们线上其实踩过 consent 脚本初始化的问题，所以后面对 tracking / consent 代码的稳定性和序列化边界更敏感。**

同类还有一个更近期的例子：UTT 的初始化脚本加了加载后检测——如果第三方 stub 没接管队列，就主动上报 Sentry。也就是说**埋点脚本自己的加载失败也被纳入了监控**，这就是从踩坑里长出来的治理动作。

**9. 埋点的工程治理：怎么保证几百个事件长期不腐化（高阶加分项）**

如果面试官是架构向的，这块能从“接 SDK”直接拉到“治理体系”：

1. **新增事件有强制流程**：不是随手加——触发场景（fired when）必须由人确认（DOM 事件还是生命周期？once 还是 debounced？要不要去重？），然后 6 个文件同步落地：docs、schema、trigger、domain event、listener、UI dispatch，文档永远最后更新（保证文档反映的是真实代码形态，不是设计稿）；
2. **修改线上事件要先出 Diff Report**：改名、改 payload、改触发时机，都要先列出 before/after、下游所有 caller（grep 结果）、影响的 dashboard/漏斗、是否向后兼容，确认后才能动代码；
3. **pageview 是唯一例外**：新 pageview 不走 redux 事件流，直接 hook 同步 push dataLayer——因为 listener 在 layout 的 useEffect 注册，子组件更早的 effect 会丢事件，而且 pageview 没有扇出价值。这条是写进规范的硬规则；
4. **AI 也要遵守**：这些规则被做成了一个 skill（tracking-event-ops），AI agent 加改埋点时必须走同样流程，防止 AI 图省事绕过治理。

一句话：

**埋点系统的长期敌人不是技术，是腐化——所以我们把“加事件、改事件”本身也变成了有流程、有契约、有审计的工作。**

**10. 这三个点合起来，面试里你到底该怎么讲**

建议你用这个逻辑：

第一句先定性：

**我们把埋点、实验和隐私看成一套统一的数据治理能力，而不是三个分散功能。**

然后分三层说：

**第一层，埋点。**  
我们按业务动作建统一事件出口，不按平台分散写逻辑。架构上是一条单向事件流：UI 只 dispatch 业务语义事件，listener 订阅后扇出到各渠道 trigger，业务侧和渠道侧完全解耦。比如 Add to Cart 成功后，会统一分发到 GA、Facebook、Pinterest、DY、Klaviyo，同一个 eventId 保证跨平台去重，而且 tracking 失败不影响主流程。

**第二层，Feature Flag / Experiment。**

**第三层，隐私。**  
我们把 consent 前置成系统闸门，没有用户同意就不加载对应脚本，CAPI 发送前也要过 consent 检查。同时把 CookieYes 的同意状态映射到 Google Consent Mode，PII 哈希后才上传，保证合规和数据采集链路一致。

**13. 三个最常见追问的完整回答**

### 追问 1：为什么埋点要按业务动作统一收口，而不是各平台自己发？

三个理由，层层递进：

1. **口径一致性**：各平台自己发，同一个"加购"在 GA 和 FB 里字段、时机、去重都不一样，数据对不上是迟早的事。统一收口后，一次业务成功、一份上下文、一个 eventId，各渠道只是映射层；
2. **变更成本**：改一个业务动作（比如加购 payload 加个字段），收口前要在 5 个平台代码里改 5 处还难免漏；收口后只改事件定义和各 trigger 的映射，而且有 TS schema 编译期兜底；
3. **主流程隔离**：统一层才能做"失败只记日志、多渠道 allSettled、keepalive"这些可靠性设计。散在各页面里，每个开发者的处理质量参差不齐。

反过来说，收口也有成本——多一层抽象、listener 是全局单点。所以我们的边界是：**无扇出价值的不走总线**（pageview 是唯一例外，直接 push），**纯单渠道的轻量曝光类也不强行收口**。

### 追问 2：Feature Flag 和 Experiment 在工程上怎么区分？

概念上有交集，但工程职责不同：

- **Feature Flag 管"系统行为"**：这个功能对谁开、什么时候开、出了问题怎么关。求值维度是市场/渠道/环境/时间窗，生命周期跟着发布走，最终会被删掉（功能全量后移除 flag）；
- **Experiment 管"效果度量"**：核心是分流 + 归因——用户落到哪个 variant 必须和后续的曝光、点击、转化数据打通，实验结束要回答"哪个 variant 更好"。生命周期跟着实验周期走。

工程上的交叉点：experiment 的 variant 下发经常复用 flag 基础设施，但**实验语义（experimentId、variant、曝光上报）是独立的埋点契约**，不会混进功能开关里。我们项目里 flag 是构建期静态求值（按市场），实验分流则靠 DY 这类平台运行时下发，两套并存。

### 追问 3：隐私合规为什么一定要做到“脚本加载前”而不是“事件发送前”？

因为"事件发送前拦截"有三个堵不住的洞：

1. **脚本加载本身就在采集数据**：第三方脚本一下载执行，IP、UA、指纹这些信息已经出去了——你后面拦不拦事件都改变不了这个事实，GDPR 视角下这已经是数据处理行为；
2. **拦截点永远打不全**：脚本一旦跑起来，它自己发的请求（beacon、像素、websocket）你没法逐个审查，你拦的只是"你知道的那几个"；
3. **合规审计看的是行为不是意图**：跟审计解释"我们加载了脚本但没发事件"远不如"未经同意脚本根本没有加载"干净。

所以我们的闸门分三层，越靠前越根本：脚本加载前（consent default + script gate）> 组件渲染前（useConsent）> 事件发送前（checkConsentGranted 兜底）。事件发送前的检查不是主力，是防线最后一环——防止有脚本绕过前两层。

### 追问 4（加练）：事件丢了或重复了，你们怎么发现和防？

防重复三个手段：listener 层按业务键幂等（purchase 按 orderId 进 Set）；event_id 一次生成多渠道共用，服务端 pixel↔CAPI 去重；hook 层 `usePageViewOnce` 保证 mount 只发一次。

防丢失两个手段：CAPI 请求带 `keepalive` 防页面卸载中断；失败进日志/Sentry（UTT 脚本加载失败主动上报），让"埋点没发出去"这件事本身可观测。

发现层面：dataLayer 有 GTM Preview 抓包样本存在文档里做基准；新事件上线前要过 QA checklist（demo 里的模板就是干这个的）。

### 追问 5（加练）：SSR/水合场景下埋点有什么坑？

最典型的是 pageview：Redux listener 是在 layout 的 `useEffect` 里注册的，但子组件里 mount 即发的逻辑（`useLayoutEffect`）比它先跑——走 redux 的 pageview 会丢首帧。所以我们规定 pageview 不走事件总线，用 hook 同步直推 dataLayer。这个例子面试很好用，因为它说明**事件总线不是银弹，时序敏感场景要留旁路**，而且我们把这条写成了硬规则防止后人踩坑。
