我把团队长期重复遇到的问题，从依赖个人经验，变成了可复用、可验证、可持续治理的平台能力。

## 开场

如果让我选两件最有挑战、也最有成就感的工作，我会讲两个方向。

一个是组件驱动设计，主要解决多团队、多市场下的研发效率和体验一致性问题；另一个是 Sentry 错误监控治理，主要解决线上问题发现以后，噪音大、定位慢、责任边界不清晰的问题。

这两件事情看起来一个偏研发效率，一个偏稳定性，但我觉得共同点是：它们都不是只解决一次具体问题，而是把团队依赖个人经验的工作，沉淀成一套长期可复用的工程机制。

---

## 案例一：组件驱动设计

我们项目同时面向多个市场，也有 Web、POS、不同品牌主题以及新旧版本并存。

最开始比较明显的问题是，同一个按钮、表单或者弹窗，在不同业务模块中可能有不同实现。短期看，每个人直接在页面里写是最快的；但项目扩大以后，就会出现样式不一致、交互行为不一致，以及一个基础样式改动影响很多页面的问题。

所以我们后面做的并不只是“封装几个组件”，而是希望建立一条完整的设计系统交付链路。

首先，在组件设计上，我们会区分基础组件和业务组件。

基础组件像 Button、Input、Dialog，本身不包含业务逻辑，重点是 API、状态、响应式、键盘操作和可访问性。业务组件则是在基础组件上组合业务规则，比如 Payment Button 会根据支付状态、库存、权限等字段决定 Disable 和 Loading。

这个边界很重要。如果所有业务逻辑都塞进基础组件，组件会越来越万能，也越来越难维护；但如果完全不做抽象，各业务模块又会重复开发。

第二，我们把样式从组件代码中继续向下抽象成 Token。

底层是颜色、字号、间距等基础 Token；中间是 Primary、Danger、Surface 这样的语义 Token；最后再映射到具体组件的 Hover、Active、Disabled 状态。

这样品牌升级或者主题变化时，我们修改的是语义映射，而不是全项目搜索某个颜色值。业务使用的也是 `primary` 这种语义，而不是依赖底层 UI Library 的具体实现。

第三，在开发流程上，我们使用 Component-Driven Development。

组件会先在 Storybook 中独立开发，把不同尺寸、状态、主题、交互和边界情况展示完整，再进入业务页面。Storybook 不只是展示组件，也同时承担组件文档、交互验证和设计沟通的作用。

在 PR 阶段，我们还通过 Chromatic 做视觉回归。组件发生变化以后，可以直接看到哪些 Story 出现视觉差异，判断变化是不是符合预期。

这里比较有挑战的地方是，基础 Token 或基础组件一改，可能会产生几百个视觉 Diff。如果全部人工逐张检查，成本很高；但如果为了减少 Diff 而不做全量验证，又可能漏掉跨页面影响。

所以我们的处理方式是对变更进行分级：

- 普通叶子组件改动，只验证相关 Story。
- 修改默认行为或者组件 Token，需要扩大回归范围。
- 修改全局语义 Token，则需要完整检查影响面。
- 视觉变更和行为变更尽量拆开，减少 Review 成本。

我们也尽量通过新增 Variant 来扩展能力，而不是轻易修改 Default Behavior。

我觉得这件事情最大的挑战其实不是写组件，而是平衡“统一约束”和“业务开发效率”。

约束太少，组件库会逐渐失去标准；约束太强，业务为了赶需求就会绕开组件库。所以我们既提供语义化、受约束的标准 API，也保留必要的 `slotProps`、`sx` 等扩展出口，但这些出口不应该成为默认使用方式。

最后带来的价值，一方面是多市场、多页面的体验更加一致；另一方面是组件改动的影响范围变得可见、可验证。新业务不需要重复实现基础交互，设计、开发和测试也有了共同的组件说明书。

如果要总结这个项目，我会说：

> 我最有成就感的不是完成了多少个组件，而是把组件从一段可复用代码，变成了一套包含设计规范、开发方式、测试和发布门禁的交付体系。

## 案例二：Sentry 错误监控治理

第二件事情是 Sentry 错误监控治理。

我们的项目接入了比较多的第三方服务，同时有多个市场、多个业务域。最开始的问题并不是“没有错误上报”，而是错误虽然很多，但真正有行动价值的信息不够。

比如一个错误进到 Sentry 以后，我们可能知道页面报错了，但不一定马上知道：

- 它属于 Product、Checkout 还是 Payment。
- 是我们自己的代码、接口问题还是第三方脚本。
- 影响哪个市场和页面。
- 严重程度怎么样。
- 应该由谁负责。
- 是否需要马上告警。

如果这些信息缺失，Sentry 最后很容易变成一个错误仓库，团队每天收到很多告警，但真正需要处理的问题反而被噪音淹没。

所以我们的目标不是简单提高上报数量，而是让每条错误在进入 Sentry 前就具备可分类、可路由和可行动的上下文。

第一步是统一错误入口。

业务代码不再直接调用裸的 `captureException`，而是走统一封装。这个入口负责把不同形态的错误标准化，并补充 `domain`、`pageType`、`priority`、`severity`、market、release 等上下文，同时过滤敏感信息。

第二步是在 `beforeSend` 中统一做 Error Bucket 分类。

分类最关键的设计是：它必须是一条互斥的单向决策链，一个错误只能进入一个主要类别。

客户端大致按照 Hydration、第三方、网络、API 5xx、API Timeout、应用主动上报、JavaScript Fatal、未分类的顺序判断；服务端则使用 Upstream 5xx、Upstream Timeout 等服务端语义。

顺序非常重要。比如一个第三方服务请求返回 503，它既符合第三方错误，也符合 API 5xx。如果先判断 5xx，它就会进入我们自己的接口告警，造成错误路由。

所以我们的原则是：

> 先判断边界最小、特征最明确的错误，再判断更宽泛、更通用的错误类型；一旦命中就停止继续分类。

第三步是基于结构化字段进行路由和告警治理。

代码负责产生统一的 Domain、Priority 和 Error Bucket；Sentry 再根据这些字段配置 Ownership、告警阈值和通知方式。

这样 Payment 或 Checkout 的高优先级问题可以更快通知对应负责人；普通第三方噪音则可以提高阈值，避免每个偶发错误都打扰团队。

在工具分工上，我们也会区分：

- Sentry 更适合回答“为什么失败”，例如 Stack Trace、Breadcrumb 和错误代码位置。
- Datadog 更适合回答“影响有多大”，例如某个市场的错误率、成功率或者 P95 延迟是否异常。

后面我们进一步考虑 AI 辅助问题定位。统一的错误结构在这里非常重要，因为 AI 如果只拿到一段 Stack Trace，很容易扩大分析范围；但如果错误已经带有 Domain、Page Type、Error Bucket、Release 和 Priority，AI 就可以把调查范围限制在相关模块中。

不过我们不会让 AI 直接修改高风险业务或者自动上线。更合理的流程是：先获取错误证据、完成分类和风险判断，再生成分析或修复建议，最后通过测试和 PR 进入人工 Review。

这件事情最大的挑战，是平衡覆盖率和噪音。

上报太少会漏问题，上报太多又会产生告警疲劳；分类规则太宽会路由错误，规则太细又会增加维护成本。所以我们一直把它当成治理体系，而不是一次性的配置工作。

我对这件事情最有成就感的地方是：

> 我们把线上错误从“有人看到以后再去找负责人”，变成了在错误产生时就尽量完成标准化、分类、优先级判断和责任路由，让监控真正进入问题解决闭环。

## 收尾

这两个项目也比较能代表我的工作方式。

我比较关注的不只是把当前需求做完，而是会观察团队是不是在重复解决同一类问题。如果一个问题频繁出现，我会尝试把它抽象成组件、规范、工具或者自动化流程。

组件驱动设计解决的是交付的一致性和可控性，Sentry 治理解决的是线上稳定性和响应效率。它们最终都是希望让系统规模扩大以后，团队仍然能够稳定地交付和定位问题，而不是越来越依赖少数人的经验。

## CTO 可能继续追问

### 1. 这些事情怎么量化？

不要编数字，提前准备真实数据：

- 组件库覆盖多少组件、页面、市场和应用。
- 公共组件复用率或重复实现减少情况。
- Chromatic 在上线前发现过多少视觉问题。
- 新页面交付或品牌调整耗时是否下降。
- Sentry 的未分类错误比例。
- 告警数量和有效告警比例。
- 自动分配到正确 Owner 的比例。
- MTTA、MTTR 或重复 Issue 数量变化。

如果没有完整数据，可以诚实地说：

> 当时没有建立特别完整的前后对照指标，这是我认为可以改进的地方。我们能够确认复用率、视觉回归覆盖和错误路由有明显改善，但如果重新推动，我会在项目开始前先定义 Adoption、Regression Rate、Unclassified Rate 和 MTTR 作为成功指标。

### 2. 你个人具体负责什么？

这一段必须根据事实调整，不要把团队成果全部说成个人成果：

> 我主要负责的是方案设计和关键能力落地，包括组件边界、部分组件 API、Storybook/视觉回归流程，以及 Sentry 统一入口和分类标准。同时我也会和设计、业务开发、测试以及模块负责人一起推动使用。整个体系是团队共同完成的，我的核心贡献是把零散问题整理成一套可以执行和验证的方案。

### 3. 如果重新做一次，会改进什么？

> 组件体系这边，我会更早定义组件分级和 Adoption 指标，避免只关注做了多少组件，而忽略业务是否真的使用。Sentry 这边，我会更早建立分类准确率、未分类比例和 MTTR 基线，这样能够更客观地证明治理效果，而不是只依赖团队感受。

建议你不要逐字背这份稿子，只记住主线：

> 背景和业务复杂度 → 原来的痛点 → 我做了什么 → 最难的取舍 → 如何落地 → 产生的业务和团队价值 → 如果重来怎么改进。
