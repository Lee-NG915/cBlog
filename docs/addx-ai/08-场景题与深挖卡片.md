## 卡片 A：架构重构（首选）

**一句话**：legacy 按页面堆叠 → 域 + 三层 + Nx tag 可执行边界；Flag 控灰度。

**可被追问的事实**

- Web/POS 共用领域能力，展示层不同。  
- 域：Product、Cart、Checkout、Payment、Promotion、Order、Search…  
- tag + lint/CI，不是只靠文档。  
- 灰度与新旧共存。

**高概率追问 → 要点**

- 为何按域不按 hooks/api？→ 改动按业务归属。  
- 三层职责？→ 状态 / 编排 / UI。  
- 跨域下单？→ 上层编排，domain 不互调。  
- tag 防啥不防啥？→ 防依赖方向，不防烂抽象。  
- 收益怎么证？→ affected 范围、违规数、交付/回归，承认学习成本。  
- 重做调啥？→ 域粒度、composite 边界、payment 额外层。

**别踩坑**：只背名词无边界冲突；声称零耦合；只讲结构不讲迁移回滚。

## 卡片 B：ISR + Redis / 搜索缓存（首选）

**一句话**：多 Pod Redis 共享 Full Route Cache（1s 超时→LRU）；搜索用 `responsesCache` 2min/100 去重。

**可被追问的事实**

- `cacheHandler` + `cacheMaxMemorySize:0`；prefix=`env-buildId`。  
- `timeoutMs:1000`；connect 无超时是已知限制。  
- 搜索权威代码：`search-client.ts`（旧 search-result-cache 文档过时）。  
- INP attribution tags：`inpPhase` / `inpBottleneck`。

**高概率追问 → 要点**

- 自带缓存不够？→ 单机，多 Pod 重复生成。  
- key？→ env/buildId/market/locale/currency；慎用户态。  
- Redis 挂了？→ 快速失败 + LRU；承认跨 Pod 不一致。  
- 搜索两层？→ 结果 TTL + in-flight Promise 去重。  
- 旧简历数字？→ 勿背 5min/30%；讲现行参数与问题动机。  

**别踩坑**：Redis 当 DB；串市场；把过时文档当 SLA。

## 卡片 H：购物车状态管理（电商核心）

**一句话**：Redux slice + RTK Query 管 cart CRUD；乐观更新 + 多 Tab 同步 + 离线合并。

**追问要点**

- 状态放哪？→ Redux slice 持有 cart state；RTK Query 管 API 缓存和请求生命周期；cookie 存 cart token 保证跨刷新。
- 乐观更新怎么做？→ `onQueryStarted` 里先 `updateQueryData` 改本地 → API 失败 `patchResult.undo()` 回滚。好处：用户无延迟感；风险：回滚时 UI 闪回。
- 多 Tab 同步？→ `BroadcastChannel` / `storage` event / cookie 轮询。项目中 cart state 走 Redux，跨 Tab 需要监听 storage 或重新 fetch。
- 离线 → 在线？→ 本地队列存操作（add/remove/update qty），上线后依次回放；冲突靠服务端 merge（last-write-wins 或版本比较）。
- 项目联动：`addedCartActionSucceededEvent` dispatch 后 tracking listener 才触发埋点 → cart 操作失败不会发埋点。

**别踩坑**：把整个 cart 存 localStorage 当持久化（token 过期、数据过时）；乐观更新不做回滚。

## 卡片 I：长列表 / 无限滚动（搜索页、PLP）

**一句话**：虚拟滚动只渲染可视区域；IntersectionObserver 触发分页加载；缓存去重防重复请求。

**追问要点**

- 虚拟滚动原理？→ 容器高度 = `totalItems × itemHeight`；只渲染 `startIndex ~ endIndex` 的 DOM；scroll 事件更新可见范围。
- 固定高度 vs 动态高度？→ 固定：计算简单 O(1)。动态：需要 `measureElement` + 位置缓存（`react-virtuoso` 内置支持）。
- IntersectionObserver vs scroll 事件？→ IO 性能更好（浏览器原生、不阻塞主线程、throttle 内置）；scroll 需要手动 throttle。
- 项目联动：搜索页用 Algolia InstantSearch 管分页 + `responsesCache`（2min/100）去重请求。不是纯虚拟滚动，是 load more + 缓存。
- SEO？→ SSR 渲染首屏数据；客户端 load more 部分 SEO 不敏感。

**别踩坑**：万级列表不做虚拟化直接全渲；scroll 事件不 throttle；不处理快速滚动导致白屏。

## 卡片 J：第三方脚本治理（GTM / DY / CookieYes）

**一句话**：`next/script` 控加载时机；Consent 闸门拦未授权脚本；INP attribution 归因第三方性能影响。

**追问要点**

- 加载策略？→ `next/script` 三种 strategy：`afterInteractive`（hydration 后，默认）、`lazyOnload`（空闲时）、`worker`（Web Worker 隔离）。GTM 通常 `afterInteractive`；分析类可 `lazyOnload`。
- 阻塞主线程？→ 第三方脚本是 INP/TBT 主要元凶之一。项目 INP attribution 有 `responsibility` 字段区分 `own / 3p_critical / 3p_other / extension`。
- hydration mismatch？→ **真实案例**：CookieYes 在 hydration 前直接改 DOM → React 对比发现不一致 → 整棵树重新渲染或报错。解法：延后加载到 hydration 完成后。
- Consent 闸门？→ `CookieYesScriptGate` + `useConsent` / `checkConsentGranted`；**无同意不加载对应脚本**（不是加载了不发事件）。分类：necessary / analytics / advertisement / functional。
- 项目联动：DY / Algolia / Stripe / PayPal 是关键三方（`CRITICAL_THIRD_PARTY_PATTERNS`），错误**不进** `third_party` bucket，单独被告警规则覆盖。

**别踩坑**：所有第三方同步加载；不区分关键/非关键三方；consent 只是 UI 没有实际拦截。

## 卡片 K：电商图片优化

**一句话**：`next/image` 自动格式 + 尺寸 + lazy；CDN 变换按需裁切；hero image 设 priority 救 LCP。

**追问要点**

- `next/image` 做了什么？→ 自动 WebP/AVIF 格式协商；`srcset` + `sizes` 按设备宽度选图；默认 `lazy loading`（viewport 外不加载）；防 CLS（需指定 width/height 或 `fill`）。
- LCP 优化？→ hero image / 首屏大图设 `priority={true}` → Next 自动加 `<link rel="preload">`；其余图默认 lazy。
- CDN 图片变换？→ URL 参数指定 width/quality/format → CDN 边缘实时裁切缓存 → 同一张原图生成多个变体。
- 响应式图片？→ `sizes="(max-width: 768px) 100vw, 50vw"` 让浏览器按 viewport 选合适 srcset → 移动端不下载 PC 大图。
- 项目联动：PDP hero image 设 priority；PLP 产品卡片图 lazy；Storyblok CMS 图片走 CDN 变换。

**别踩坑**：所有图都 priority（失去 lazy 优势）；不指定尺寸导致 CLS；原图直出不走 CDN 变换。

## 卡片 L：搜索自动补全设计

**一句话**：debounce + abort 防竞态；最近结果 Map 缓存；键盘可导航；高亮匹配文本。

**追问要点**

- 竞态怎么防？→ 每次输入创建新 `AbortController`，先 `abort()` 上一次请求；结合 debounce（200-300ms）减少请求频率。
- 缓存？→ `Map<query, results>` 或 LRU 缓存最近 N 条结果；完全匹配直接返回，不发请求。与项目 `responsesCache` 同一思想。
- 键盘导航？→ `ArrowDown/Up` 移动高亮索引；`Enter` 选中；`Escape` 关闭。用 `aria-activedescendant` + `role="listbox"` 做无障碍。
- 高亮匹配？→ 按 query 切分结果文本 → 匹配部分用 `<mark>` 或 `<strong>` 包裹。注意：正则需转义特殊字符。
- 空状态 / 错误？→ 空结果展示"无匹配"；请求失败不清空上次结果（降级体验）；loading 状态可选展示或不展示。
- 项目联动：搜索页用 Algolia InstantSearch 的 searchBox → 内置 debounce + 请求管理；`responsesCache` 做结果缓存。

**别踩坑**：不 debounce 每键一请求；不 abort 旧请求导致结果闪烁；键盘导航不做无障碍。

## 通用场景题（非 Shopify）

### 没有某平台经验为何能胜任？

- 承认缺口。  
- 迁移的是：全球电商、模块化、性能、交易一致性、可观测。  
- 语法可学，复杂治理非从零。

### 你有全栈经验吗？

- 高级前端 + BFF；列举 Server Actions/Redis/鉴权/支付幂等。  
- 数据库/独立服务非主责；区分做过/参与/在学。

### 如何设计全球化缓存 Key？

- 资源 + market/country/language/currency + 筛选。  
- 用户态不进公共缓存。  
- Tag 失效 + TTL。

### 从业务交付到平台架构？

- 问题驱动：UI 漂移→Token/Chromatic；多 Pod→Redis；乱依赖→Nx tag；支付重试→幂等。  
- 有代价：学习成本、一致性取舍。

### 灰度发布怎么做？

- Flag 三层；监控核心指标；瞬关回滚；再删旧代码。

### 线上支付失败怎么排查？

- Datadog 看成功率/市场/版本 → Sentry 看栈与 bucket → traceId/idempotencyKey 对单笔 → 区分第三方成功与订单状态 → 降级/Flag。

### 性能优化从哪开始？

- RUM CWV → 归因 LCP/INP/CLS 或接口/Bundle → 改 → 同维度对比验证。

## 比心直播经历（各 1 分钟版）

按你真实经历填细节；无则改成「活动大促/电商峰值」同类叙事，勿编造。

### 高并发活动前端保障

- 问题：峰值流量、接口打满、首屏与脚本争主线程。  
- 做：静态/ISR 扛展示；限流与降级开关；非关键 SDK 延后；核心路径监控与回滚 Flag。  
- 结果：可用性优先，接受非核心功能降级。

### WebSocket

- 场景：实时状态（库存/直播互动/消息）。  
- 点：重连退避、心跳、断线队列、与 HTTP 降级、鉴权与房间隔离。  
- 坑：扇出压力、背压、乱序。

### Canvas

- 场景：可视化/动效/导出。  
- 点：分层绘制、离屏、节流 rAF、内存与清晰度（DPI）、销毁监听防泄漏。  
- 与 DOM：高频变化用 Canvas，复杂可访问性仍要 DOM 兜底。
