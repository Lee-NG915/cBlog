## 1. Joyboy 中的 DDD 解决了什么问题？

### 推荐回答

Joyboy 引入 DDD，主要是为了解决 Legacy 项目中业务代码混在一起、模块边界不清晰，以及一个需求修改后影响范围难以控制的问题。

我们首先按照 Product、Cart、Checkout、Payment、Promotion 等业务域横向拆分，再在每个业务域内部按照 Components、Services、Domain 做技术分层。

- Components：负责 UI、用户交互和事件派发，不承担复杂业务编排。
- Services：负责业务流程编排，包含 Command、Helper 和 Redux Listener。
- Domain：负责状态、实体、类型、RTK Query API 和业务事件定义。

依赖方向保持单向：Components 可以依赖 Services 和 Domain，Services 可以依赖 Domain，但 Domain 不能反向依赖 Services 或 Components。这些规则通过 Nx Tag 和 ESLint Module Boundary 执行，而不只是团队口头约定。

典型跨域流程是：Component 派发业务事件，Service Listener 订阅事件并编排，再调用相应 Domain API 或更新状态。需要组合多个业务域时进入 Composite；Shared 只承载真正通用、不能依赖具体业务域的能力。

它的收益是边界清晰、修改影响范围可控、Ownership 更明确。代价是学习成本提高、一次业务流程可能分散在多个文件中，并且必须防止 Listener、Shared 和 Composite 变成新的上帝模块。

### 架构图

```mermaid

    subgraph Domains["横向业务域"]
        Product["Product"]
        Cart["Cart"]
        Checkout["Checkout"]
        Payment["Payment"]
        Promotion["Promotion"]
    end

    subgraph Layers["单个业务域的纵向分层"]
        Components["Components<br/>UI / Interaction"]
        Services["Services<br/>Command / Listener / Orchestration"]

    Composite --> Checkout
    Composite --> Payment
    Composite --> Promotion
```

### 速记句

> DDD 不是调整文件夹，而是通过业务边界、单向依赖和跨域编排规则控制复杂度。

## 2. Cart 使用 Promotion 能力时，如何避免跨域强耦合？

### 推荐回答

首先明确能力归属：优惠券规则和操作属于 Promotion，Cart 只负责表达“用户希望对购物车使用某张优惠券”。

如果只是简单调用，页面可以通过 Promotion 暴露的稳定 Command 或 Domain Action 发起操作，但传入的 Payload 必须包含 Promotion 完成业务所需的数据，Promotion 不应该反向读取 Cart State。

如果中间涉及 Cart 与 Checkout 两套数据源选择、字段转换或不同场景逻辑，则把适配放到 Composite Adapter。Composite 可以同时依赖 Cart、Checkout 和 Promotion，负责把不同业务域适配成 Promotion 接受的统一契约。

Promotion 不兼容 Cart 的内部模型；Cart 也不理解 Promotion 的具体实现。成功后由 Promotion 派发领域事件，其他 Listener 再处理刷新、通知或埋点。

### 调用图

```mermaid
sequenceDiagram
    participant UI as Cart / Checkout UI
    participant Adapter as Composite Adapter
    participant Promotion as Promotion Command
    participant API as Promotion API
    participant Listener as Listeners

    UI->>Adapter: 用户应用优惠券
    Adapter->>Adapter: 选择数据源并转换契约
    Adapter->>Promotion: couponCode + 场景 + 调用契约
    Promotion->>API: 应用优惠券
    API-->>Promotion: 返回结果
    Promotion-->>Listener: 派发成功领域事件
    Listener->>Listener: 刷新 / 通知 / 埋点
```

### 速记句

> 能力归所属领域，跨域适配放 Composite，调用方传完整契约，提供方不反向读取调用方状态。

## 3. POS Stripe Terminal 新支付链路如何工作？

### 推荐回答

支付开始前订单已经创建，并且拥有 Order ID 和 Order Number。

用户选择 Stripe Terminal 后，前端首先检查 Reader 是否连接，然后调用 Initiate 接口创建内部支付记录和 Stripe PaymentIntent。后端返回内部 `paymentId` 以及 Stripe `clientSecret`。

前端使用 `clientSecret` 调用 Stripe Terminal SDK：

1. `collectPaymentMethod`：让终端读取银行卡。
2. `processPayment`：处理 Stripe 支付。
3. 成功后获得 Stripe `paymentIntentId` 和 External Reference。

随后前端调用 Confirm Payment，提交内部 `paymentId`、Stripe `paymentIntentId` 和 External Reference，让后端确认并保存支付结果。确认成功后刷新 Payment Method List。

需要区分：

- `paymentId`：内部 POS Payment 记录。
- `paymentIntentId`：Stripe 侧 PaymentIntent。
- Confirm Payment：确认当前支付方式。
- Complete Payment：后续完成整个订单，不能与 Confirm 混为一谈。

Initiate 和 Confirm 都需要幂等键。对于同一个逻辑请求的重试，应复用相同幂等键，而不是每次生成新键。

### 支付时序

```mermaid
sequenceDiagram
    actor User as 用户
    participant Web as POS Web
    participant Backend as Payment Backend
    participant Terminal as Stripe Terminal SDK
    participant Stripe as Stripe

    User->>Web: 选择 Terminal 并点击支付
    Web->>Web: 检查 Reader 连接
    Web->>Backend: Initiate(orderId, amount, idempotencyKey)
    Backend->>Stripe: 创建 PaymentIntent
    Stripe-->>Backend: clientSecret
    Backend-->>Web: paymentId + clientSecret
    Web->>Terminal: collectPaymentMethod(clientSecret)
    Terminal-->>Web: PaymentIntent
    Web->>Terminal: processPayment(PaymentIntent)
    Terminal->>Stripe: 处理支付
    Stripe-->>Terminal: 支付结果
    Terminal-->>Web: paymentIntentId + externalReference
    Web->>Backend: Confirm(paymentId, paymentIntentId, idempotencyKey)
    Backend-->>Web: Confirm success
    Web->>Backend: 刷新 Payment Method List
```

### 速记句

> 内部 `paymentId` 管业务记录，Stripe `paymentIntentId` 管渠道支付，幂等键管重复请求，失败补偿管中间状态。

## 4. 如何避免异步支付清理被执行多次？

### 推荐回答

每次 Initiate 都生成独立 `paymentId`，取消和删除必须携带该 ID，确保清理范围只落在当前支付记录。

UI 的 Loading 或 Disabled 可以防止用户连续点击，但不能解决用户取消、SDK 失败回调、超时处理同时发生的异步并发问题。

前端还需要把支付过程设计为单向状态机。第一个清理流程开始时，立即把状态从 Pending 原子地切换到 Cancelling，并消费当前待清理标识；后续回调发现它已经被消费，就不再重复执行。不能等异步取消完成后才修改状态。

服务端删除接口也要幂等。同一 `paymentId` 被重复清理时，应返回相同最终结果，而不是产生新的副作用。

### 状态图

```mermaid
stateDiagram-v2
    [*] --> Initiating
    Initiating --> Pending: initiate success
    Initiating --> Failed: initiate failed
    Pending --> Confirming: SDK success
    Pending --> Cancelling: 用户取消 / SDK失败 / 超时
    Cancelling --> Cancelled: 幂等清理完成
    Confirming --> Success: confirm success
    Confirming --> Cancelling: confirm failed
    Success --> [*]
    Cancelled --> [*]
    Failed --> [*]
```

### 速记句

> Loading 防重复点击，状态机防前端并发，接口幂等保证最终一致性。

## 5. 为什么统一封装 Sentry 错误上报？

### 推荐回答

统一封装的目标，是把错误上报从“各业务模块自由发挥”变成可治理的工程标准。

业务主动上报统一走结构化入口，完成错误标准化、PII 过滤、日志记录，并补充 Domain、Page Type、Priority、Severity 和业务 Tags。

但并非所有错误都会经过主动上报入口。运行时异常、Promise 异常和第三方脚本错误仍可能被 SDK 自动捕获，因此还需要在 `beforeSend` 对所有进入 Sentry 的错误做第二层治理：

- 降噪和第三方过滤。
- 上下文补充。
- `error_bucket` 互斥分类。
- Ownership 和告警路由。

结构化字段不仅服务人工排查，也给 AI 自动修复提供稳定输入。AI 可以根据 Domain、Page Type、Error Bucket、Priority 和堆栈判断问题归属、风险等级和允许修改范围，再决定自动创建 PR 还是升级人工处理。

### 治理链路

```mermaid
flowchart LR
    Active["业务主动上报"] --> Capture["结构化 Capture<br/>Normalize / PII / Context"]
    Auto["运行时自动捕获"] --> BeforeSend
    Capture --> BeforeSend["beforeSend<br/>降噪 / 补充 / 分桶"]
    BeforeSend --> Sentry["Sentry Issue"]
    Sentry --> Alert["互斥告警"]
    Sentry --> Owner["Ownership 路由"]
    Sentry --> Runbook["Runbook"]
    Sentry --> AI["AI 分析 / 有界修复 / PR"]
```

### 速记句

> 主动上报入口保证数据标准化，`beforeSend` 治理全部错误，结构化标签驱动告警、Ownership 和修复闭环。

## 6. 如何设计互斥的 Error Bucket？

### 推荐回答

错误分类不是给一个错误同时添加多个类别，而是建立一条有明确优先级的单向决策链。每个错误按照固定顺序判断，命中一个类别后立即返回。

顺序要优先考虑语义明确程度和告警价值。例如第三方请求即使返回 500，也应该优先归入 Third Party，否则会污染自己的 API 5xx 告警；主动上报的请求如果明确发生超时，也应先归入 Timeout，而不是宽泛的 App Error。

客户端顺序：

```text
Hydration → Third Party → Network → API 5xx → API Timeout
→ App Error → JS Fatal → Unclassified
```

服务端顺序：

```text
Upstream 5xx → Upstream Timeout → JS Fatal
→ App Error → Unclassified
```

还应记录 Bucket Confidence。状态码等强证据标记高置信度，依赖错误名称或字符串推断的分类降低置信度。

### 客户端决策树

```mermaid
flowchart TD
    E["Error"] --> H{"Hydration?"}
    H -->|Yes| HB["hydration"]
    H -->|No| T{"Third Party?"}
    T -->|Yes| TB["third_party"]
    T -->|No| N{"Network?"}
    N -->|Yes| NB["network"]
    N -->|No| A5{"API 5xx?"}
    A5 -->|Yes| A5B["api_5xx"]
    A5 -->|No| AT{"Timeout?"}
    AT -->|Yes| ATB["api_timeout"]
    AT -->|No| AE{"Explicit Capture?"}
    AE -->|Yes| AEB["app_error"]
    AE -->|No| JF{"JS Fatal?"}
    JF -->|Yes| JFB["js_fatal"]
    JF -->|No| U["unclassified"]
```

### 速记句

> Error Bucket 是按照业务语义和告警价值排序的互斥决策树，不是并列标签。

## 7. 多 Pod 为什么需要 Redis 共享 ISR 缓存？

### 推荐回答

如果每个 Pod 只使用本地 ISR 缓存，同一页面会在不同实例中拥有不同缓存。负载均衡把用户请求分发到不同 Pod 时，可能返回不同版本的数据；多个 Pod 也可能同时回源和重新生成相同页面。

因此使用 Redis 作为共享 Full Route Cache，让所有实例读取同一份缓存结果。

Redis Key 必须进行环境和版本隔离。加入部署环境与 Build ID，可以避免测试、生产和不同构建版本互相污染。多市场也必须通过独立环境、命名空间或业务 Key 隔离，尤其不能错误共享价格、语言和 CMS 内容。

缓存失效采用 Tag 和 Path 两种粒度。CMS 发布 Webhook 到达后，应用根据 Content Type 或 Slug 调用 `revalidateTag`；路由结构强相关时调用 `revalidatePath`。底层 Cache Handler 根据关联关系失效缓存。

Redis 故障时降级到进程内 LRU，保障服务继续可用。但 LRU 不再跨 Pod 共享，会重新出现短暂不一致和重复回源，因此还要监控 Redis 状态、降级次数、命中率和上游请求量。

### 缓存架构

```mermaid
flowchart TD
    User["用户请求"] --> LB["Load Balancer"]
    LB --> P1["Pod A"]
    LB --> P2["Pod B"]
    LB --> P3["Pod C"]
    P1 --> Redis[("Redis Shared Cache")]
    P2 --> Redis
    P3 --> Redis
    Redis --> Origin["CMS / API"]
    Webhook["Storyblok Webhook"] --> Revalidate["revalidateTag / revalidatePath"]
    Revalidate --> Redis
    Redis -. "连接失败" .-> LRU["各 Pod 本地 LRU 降级"]
```

### 速记句

> Redis 解决跨实例一致性和命中率，Tag 解决新鲜度，LRU 解决 Redis 故障时的可用性。

## 8. 为什么搜索还要缓存进行中的 Promise？

### 推荐回答

缓存已经完成的响应，只能解决先后发生的重复请求。当前一个请求尚未返回时，响应缓存里还没有结果，并发到达的相同请求仍会重复访问后端。

解决方式是 Request Coalescing / Single Flight：

1. 第一个请求创建网络 Promise。
2. 按完整查询参数把 Promise 放入缓存。
3. 后续相同请求直接等待同一个 Promise。
4. 成功后结果在 TTL 内继续复用。
5. 失败后删除缓存，避免永久复用 Rejected Promise。

缓存 Key 必须包含 Query、Filter、Facet、Page 等完整条件，防止不同搜索错误共享结果。

这与 Stale-While-Revalidate 不同：前者让并发请求等待同一个新结果；后者可以先返回旧数据，再后台更新。

### 请求合并图

```mermaid
sequenceDiagram
    participant A as 调用方 A
    participant B as 调用方 B
    participant Cache as Promise Cache
    participant API as Search API

    A->>Cache: search(key)
    Cache->>API: 创建 Promise P
    B->>Cache: search(same key)
    Cache-->>B: 返回同一个 Promise P
    API-->>Cache: Response
    Cache-->>A: 同一结果
    Cache-->>B: 同一结果
```

### 术语纠偏

- 单个热点 Key 失效并引发并发回源：缓存击穿 / Stampede。
- 大量 Key 同时失效：缓存雪崩。
- 多个相同请求共享一个 Promise：Single Flight / Request Coalescing。

### 速记句

> 响应缓存解决连续重复，Promise 缓存解决并发重复。

## 9. 只有一个海外市场变慢，如何排查并验证？

### 推荐回答

第一步不是直接看某台服务器，而是通过 RUM 按国家、页面、设备、浏览器、版本、ISP 和网络类型拆分数据，确认影响范围。

然后根据指标定位层次：

- TTFB 上升：检查 Pod CPU、内存、Event Loop、请求排队、Redis 命中率、LRU 降级和上游 API Trace。
- TTFB 正常但 LCP 变差：检查 CDN、DNS、静态资源、图片、字体、首屏资源优先级和市场专属 CMS Payload。
- INP 变差：检查 Long Task、Hydration、重复渲染、第三方脚本和首屏 JavaScript。
- Sentry 异常增加：检查页面是否进入降级、重试或重复请求逻辑。

如果与发布高度相关，优先关闭 Feature Flag 或按市场回滚。如果没有发布，更应该检查配置、数据量、流量、第三方服务、CDN 和后端变化，不能直接认定为代码问题。

修复后在相同市场、页面、设备维度对比 TTFB、LCP、INP、缓存命中率和错误率，关注 p75、p95，并结合 RUM 与合成测试确认改善持续存在。

### 排查决策图

```mermaid
flowchart TD
    Start["单市场性能变差"] --> Scope["按市场 / 页面 / 设备 / 版本 / ISP 切分"]
    Scope --> Metric{"哪个指标变差?"}
    Metric -->|TTFB| Server["Pod / Redis / Trace / Upstream API"]
    Metric -->|LCP| Delivery["CDN / DNS / 图片 / 字体 / CMS Payload"]
    Metric -->|INP| Client["Long Task / Hydration / JS / Third Party"]
    Metric -->|Error Rate| Error["Sentry / 降级 / 重试逻辑"]
    Server --> Fix["修复或止血"]
    Delivery --> Fix
    Client --> Fix
    Error --> Fix
    Fix --> Verify["同维度对比 p75 / p95 + RUM + Synthetic"]
```

### 速记句

> 先切分影响范围，再用 TTFB、LCP、INP 判断网络、服务端、资源还是客户端，最后在同一维度量化验证。

## 10. 基础组件、业务组件和页面组件如何划分？

### 推荐回答

判断维度包括业务语义、依赖关系、复用范围和需求稳定性。

基础组件是设计系统中的通用原子能力，例如 Button、Input、Drawer。它不包含业务概念，也不能依赖业务 Domain 或 Service，主要封装视觉、交互、响应式、主题和无障碍规范。

业务组件包含明确业务语义，例如 Add to Cart Button、Payment Button。它会根据商品、订单或支付状态判断 Disabled、Loading 和操作结果，可以依赖所属业务域的状态与服务。

如果一段 UI 只在一个页面使用、需求频繁变化或高度依赖当前页面上下文，则先保留在页面内部。等出现真实的第二个使用场景，并能识别稳定部分和差异点后再抽象。

不以“拆得越小越好”为目标，而是看组件是否拥有独立职责和独立变化原因。过早抽象会产生一次性组件、复杂 Props、过多条件分支和万能组件。

### 决策树

```mermaid
flowchart TD
    UI["一段 UI"] --> Stable{"需求稳定?"}
    Stable -->|No| Page["保留页面内部"]
    Stable -->|Yes| Business{"包含业务概念或依赖业务状态?"}
    Business -->|No| Reuse{"跨产品复用视觉与交互规范?"}
    Reuse -->|Yes| Base["基础组件 / Design System"]
    Reuse -->|No| Page
    Business -->|Yes| DomainReuse{"同一业务域存在真实复用?"}
    DomainReuse -->|Yes| Biz["业务组件"]
    DomainReuse -->|No| Page
```

### 速记句

> 基础组件复用视觉规范，业务组件复用稳定业务能力，需求不稳定时优先局部实现。

## 11. 共享基础组件如何发布并避免大范围回归？

### 推荐回答

先做影响评估，确认改动属于局部样式、公共 Design Token、交互逻辑还是组件 API。公共 Token、默认 Props 和交互行为的风险明显高于局部样式。

在 Storybook 中覆盖主要 Variant、Size、状态、响应式和多主题。视觉修改通过 Chromatic 审核 Diff：目标不是要求没有 Diff，而是确认所有 Diff 都符合预期，且没有影响无关状态和组件。

涉及点击、Loading、Disabled、Focus 或键盘操作时，增加 Interaction Test 或 Testing Library 测试。API 或类型变化还需要执行受影响项目的类型检查和构建，验证 Web、POS、CMS 调用方兼容。

低风险改动可以缩小测试范围，但不能完全跳过验证。即使只是 Hover 颜色，也应至少验证对应 Story、主题、Focus/Active 状态和对比度。

高风险改动先在单一页面或市场验证，再逐步扩大范围；上线后继续关注前端错误、交互指标和视觉反馈。

### 发布流程

```mermaid
flowchart LR
    Change["组件改动"] --> Impact["影响分析<br/>Token / API / Interaction"]
    Impact --> Story["Storybook 场景覆盖"]
    Story --> Visual["Chromatic Visual Diff"]
    Impact --> Behavior["Interaction / Unit Test"]
    Visual --> Affected["Affected Build / Type Check"]
    Behavior --> Affected
    Affected --> Canary["页面或市场灰度"]
    Canary --> Monitor["线上监控"]
```

### 速记句

> 低风险改动可以缩小回归范围，但共享基础组件不能因为改动看起来简单就完全跳过验证。

## 13. Feature Flag 如何支持多市场渐进式迁移？

### 推荐回答

旧链路和新链路在迁移期并存，通过 Feature Flag 按市场逐步切换。

开关尽量集中在少数边界，例如页面入口、核心 Action 和 API Adapter，避免散落在大量业务代码中。这样可以清楚知道流量从哪里进入新链路，也方便关闭开关后完整返回旧流程。

发布时先让新代码进入生产，但保持开关关闭，线上继续走旧逻辑。这样既能验证合入没有破坏旧链路，又能保持主干持续更新，避免长期重构分支。

UAT 打开目标市场开关进行完整回归；生产先选择单一市场或小流量范围，观察交易成功率、接口错误、支付异常和用户反馈，再逐步扩大。

必须区分：

- 远程运行时开关：可以不重新构建直接切换。
- `NEXT_PUBLIC_*` 构建时配置：修改后必须重新构建部署。

严重问题优先关闭 Feature Flag；如果共享代码导致旧链路也不可用，再回滚稳定版本。迁移期间新旧链路必须保持 API 和数据兼容，并同时测试 Flag On、Flag Off 和切换过程。迁移完成后及时删除旧代码和废弃开关。

### 灰度流程

```mermaid
flowchart LR
    Merge["新旧代码合入主干"] --> DeployOff["生产部署<br/>Flag Off"]
    DeployOff --> LegacyCheck["验证旧链路兼容"]
    LegacyCheck --> UAT["UAT Flag On"]
    UAT --> Market["单市场 / 小流量灰度"]
    Market --> Observe{"指标正常?"}
    Observe -->|Yes| Expand["逐步扩大"]
    Observe -->|No| Off["关闭 Flag"]
    Off --> Fix["Hotfix 或版本回滚"]
    Expand --> Cleanup["删除旧代码与废弃 Flag"]
```

### 速记句

> 先让新代码安全进入生产，再通过开关控制流量；关闭开关是业务回滚，版本回滚是最后兜底。

## 14. 新系统写入旧系统不兼容数据时，如何迁移和回滚？

### 推荐回答

重大数据库切换选择当地低流量时段，并开启维护模式，停止新的用户交易。但维护页面只是前端入口控制，服务端还必须真正关闭写入并等待进行中请求完成。

支付 Webhook、消息队列和后台任务需要暂停消费或暂存消息，避免迁移期间继续改变数据。

写入停止后创建数据快照并执行迁移。迁移完成不能只看脚本成功，还要校验订单数量、金额、支付状态和关键字段，并与支付平台对账。暂存事件在新系统启动后通过幂等机制安全重放。

数据模型优先采用 Expand-Contract：

1. 先增加新字段或新表，旧代码可以忽略。
2. 新旧系统在兼容窗口内都能读取。
3. 完成切换并稳定运行。
4. 最后移除旧字段和旧逻辑。

如果新系统已经产生大量新交易，不直接恢复旧快照，否则会丢失发布后的数据。此时应保持兼容并优先向前修复。

### 迁移流程

```mermaid
flowchart TD
    Prepare["兼容 Schema / Expand"] --> Maintenance["维护模式"]
    Maintenance --> StopWrite["服务端停止写入"]
    StopWrite --> Drain["排空进行中请求"]
    Drain --> Queue["暂存 Webhook / Queue / Job"]
    Queue --> Snapshot["创建快照"]
    Snapshot --> Migrate["数据迁移"]
    Migrate --> Validate["数量 / 金额 / 状态 / 对账校验"]
    Validate --> Replay["幂等重放事件"]
    Replay --> Canary["灰度开放新系统"]
    Canary --> Contract["稳定后 Contract / 清理旧结构"]
```

### 速记句

> 维护页面控制用户流量，服务端写保护和事件排空控制数据变化，兼容 Schema 保证能够回退。

## 15. 如何排查 React 重复渲染？

### 推荐回答

先区分重复 Render、重复 Commit、重复 Effect 和重复网络请求。组件函数中的 Console 重复打印只说明 Render，不代表 DOM 一定更新，也不代表用户可感知。

开发环境的 Strict Mode 会额外执行 Render、Effect Setup/Cleanup 和 Ref Callback，用来检查组件纯度和副作用清理。可以通过生产构建对比确认是否只发生在开发环境。

但 Strict Mode 暴露的问题不能直接忽略。Effect 重复执行导致重复请求，说明请求可能缺少取消、缓存或幂等保护；组件在生产中重新挂载时仍可能出现。

如果不是 Strict Mode，则检查更新来源：

- 自身 State。
- 父组件 Render。
- Props 引用变化。
- Context 或 Redux Selector。
- `key` 变化导致重新挂载。
- Suspense、Hydration 或路由切换。

最终使用 React DevTools Profiler 查看 Commit 耗时和更新来源，并结合 Long Task、INP 和用户可见变化判断。Render 次数多但成本低，可能完全正常。

### 排查图

```mermaid
flowchart TD
    Symptom["发现重复执行"] --> Kind{"是哪一种?"}
    Kind --> Render["Render"]
    Kind --> Effect["Effect"]
    Kind --> Request["Network Request"]
    Render --> Strict{"仅开发 Strict Mode?"}
    Effect --> Cleanup["检查依赖与 Cleanup"]
    Request --> Dedupe["检查触发源 / 取消 / 缓存 / 幂等"]
    Strict -->|Yes| Purity["检查纯函数和副作用安全"]
    Strict -->|No| Source["Props / State / Context / Selector / Key"]
    Purity --> Profile["Profiler + Commit Cost + INP"]
    Source --> Profile
    Cleanup --> Profile
    Dedupe --> Profile
```

### 速记句

> 先区分 Render、Commit、Effect 和请求，再判断 Strict Mode、更新来源和真实成本。

## 16. React.memo、useMemo、useCallback 如何选择？

### 推荐回答

- `React.memo`：组件层优化。当父组件频繁更新、子组件渲染成本较高且 Props 大多数时候不变时，通过浅比较允许 React 跳过重新渲染。
- `useMemo`：缓存计算结果。适合昂贵的数据转换、过滤、排序，或需要保持对象与数组引用稳定的场景。
- `useCallback`：缓存函数引用，不缓存函数执行结果。适合把回调传给 Memo 子组件，或函数作为其他 Hook 依赖的场景。

不能全部默认添加，因为缓存也有依赖比较、内存和理解成本。如果组件渲染很轻，缓存成本可能高于重新渲染；只要一个关键 Prop 每次都是新引用，`React.memo` 也可能失效。错误依赖还会产生 Stale Closure。

使用前先通过 Profiler 确认更新来源和渲染成本。

### 关系图

```mermaid
flowchart LR
    Parent["父组件更新"] --> Callback["useCallback<br/>稳定函数引用"]
    Parent --> Value["useMemo<br/>稳定计算结果或对象引用"]
    Callback --> Child["React.memo 子组件"]
    Value --> Child
    Child --> Decision{"Props 浅比较相同?"}
    Decision -->|Yes| Skip["跳过本次 Render"]
    Decision -->|No| Render["正常 Render"]
```

### 速记句

> `React.memo` 跳过组件渲染，`useMemo` 稳定结果，`useCallback` 稳定函数引用；只优化真实热点。

## 17. Promise、setTimeout 与页面渲染如何调度？

### 推荐回答

JavaScript 主线程只有一个调用栈。浏览器从 Task Queue 中取出一个任务执行，例如定时器回调、用户事件或消息事件。

当前任务结束后，浏览器进入 Microtask Checkpoint，清空 Promise、`queueMicrotask` 等微任务。微任务执行过程中新增的微任务也会继续执行，直到队列为空。

微任务清空后，浏览器才有机会进行样式计算、Layout 和 Paint，再进入下一轮任务。`requestAnimationFrame` 通常在下一次绘制前执行。

如果代码持续递归创建 Promise 微任务，浏览器会一直清空微任务队列，无法进入下一次渲染，也不能及时处理用户输入和定时器，造成掉帧和卡顿。

`setTimeout` 的延迟只表示最早进入队列的时间，不保证立即执行。网络下载通常不占用主线程，但回调处理、DOM 更新和绘制仍需等待主线程空闲。

### Event Loop

```mermaid
flowchart LR
    Task["执行一个 Task<br/>事件 / Timer"] --> Micro["清空全部 Microtasks<br/>Promise / queueMicrotask"]
    Micro --> RAF["requestAnimationFrame"]
    RAF --> Render["Style / Layout / Paint"]
    Render --> Next["下一轮 Task"]
    Next --> Task
    Micro -. "持续产生微任务" .-> Starve["渲染与输入饥饿"]
```

### 速记句

> 每个 Task 后先清空微任务，再获得渲染机会；持续产生微任务会饿死渲染。

## 18. TypeScript：any、unknown 和类型断言

> 本轮跳过，但属于需要补齐的基础题。

### 推荐回答

`any` 会关闭类型检查。它可以赋值给任何类型，也可以直接访问任意属性，适合迁移期的临时逃生口，但会把不安全继续传播到下游。

`unknown` 表示当前值的类型未知。任何值都可以赋给它，但在读取属性、调用方法或赋给具体类型前，必须先进行类型收窄，因此更适合 API、第三方数据和 `catch` Error。

类型断言表示“开发者告诉编译器这个值是什么类型”，它不会在运行时验证数据，也不会转换数据。只有当开发者掌握编译器无法推断的信息时才使用，不能把它当成修复类型错误的工具。

API 返回值属于运行时外部输入，仅写 TypeScript Interface 并不安全。推荐先接收为 `unknown`，再通过 Zod、Type Guard 或 Schema 校验后转换为领域类型。

`catch` 中的 Error 也应按 `unknown` 处理：

```ts
try {
  await request();
} catch (error: unknown) {
  if (error instanceof Error) {
    console.error(error.message);
  } else {
    console.error(String(error));
  }
}
```

### 对比表

| 类型 | 编译期安全 | 运行时校验 | 推荐场景 |
| --- | --- | --- | --- |
| `any` | 无 | 无 | Legacy 临时迁移、明确隔离的边界 |
| `unknown` | 有，必须收窄 | 无 | API、第三方数据、Catch Error |
| `as Type` | 由开发者承担 | 无 | 已掌握额外事实且无法自动推断 |
| Schema Parse | 有 | 有 | 外部数据进入业务域的正式边界 |

### 速记句

> `any` 放弃检查，`unknown` 延迟判断，类型断言只影响编译器，外部数据必须做运行时校验。

## 19. RSC、SSR、ISR 和 CSR 如何选择？

### 推荐回答

在 Next.js App Router 中先区分两个维度：

1. RSC / Client Component：代码在哪里运行。
2. SSR / ISR：内容什么时候生成以及如何缓存。

RSC 是默认选择，运行在服务端，不把组件 JavaScript 全部发送到浏览器，适合数据获取、内容组合以及需要访问数据库、内部服务和密钥的场景。它可以结合 Suspense 与 Streaming 分区块返回页面。

需要 `useState`、`useEffect`、事件、浏览器 API 或客户端 SDK 时，才设置 Client Component 边界。Client Component 不代表必须在客户端请求所有数据，初始数据仍可由 RSC 获取并通过 Props 传入。

SSR 表示页面在用户请求时动态生成，适合个性化、依赖 Cookie、实时性高或不适合共享缓存的数据。它不仅用于 SEO，代价是增加服务端与上游压力。

ISR 适合 Blog、CMS 落地页和部分分类页。页面先从缓存快速返回，到达 Revalidate 时间或收到 Webhook 后，再按 Tag 或 Path 重新生成。

CSR 适合强交互、浏览器环境和用户停留期间持续刷新的数据。价格、库存等可以由服务端返回初始值，再由客户端 Revalidate，不必把整个页面都变成 CSR。

实际项目通常采用混合方案。

### 决策图

```mermaid
flowchart TD
    Feature["页面或模块"] --> Browser{"需要状态、事件或浏览器 API?"}
    Browser -->|Yes| Client["Client Component"]
    Browser -->|No| RSC["Server Component"]
    RSC --> Cacheable{"公开且允许短时间旧数据?"}
    Cacheable -->|Yes| ISR["ISR / Cached RSC"]
    Cacheable -->|No| Dynamic{"个性化或强实时?"}
    Dynamic -->|Yes| SSR["Dynamic SSR / No Store"]
    Client --> Realtime{"需要持续刷新?"}
    Realtime -->|Yes| CSR["CSR Revalidation"]
    Realtime -->|No| Hydrate["服务端初始数据 + Hydration"]
```

### 速记句

> RSC/Client Component 决定代码在哪里运行，SSR/ISR 决定内容什么时候生成，CSR 负责交互和持续更新。

## 21. PDP 首屏 JavaScript 过大，如何定位与优化？

### 推荐回答

先通过 Bundle Analyzer 确认 PDP Route Chunk 的组成，按体积从大到小分析，不直接对所有代码做优化。

第一层检查 RSC 和 Client Component 边界。上层组件一旦声明为 Client Component，其下游依赖可能一起进入客户端依赖图。应确认状态、事件和浏览器 API 是否真的需要位于上层，并尽量把交互边界下沉到按钮、选择器等更小范围。

第二层检查首屏必要性。核心商品信息和购买操作需要立即加载；折叠内容、评论列表、推荐、Modal、分页和用户尚未触发的复杂功能，应通过 Dynamic Import 或交互后加载。

第三层分析大节点来源：

- Barrel Export 导致依赖图扩大。
- Tree Shaking 失效。
- 同一依赖存在多个版本。
- 图标或工具库整包引入。
- 埋点、支付 SDK、富文本或轮播库过早加载。

在 Network 中筛选 JavaScript 并按 Size 排序，对比直接刷新 PDP 与从 PLP 客户端导航到 PDP 时新增的 Chunk，以区分应用公共 Bundle 和 PDP Route 增量，也要注意 Next.js Prefetch 是否提前加载。

优化后不能只比较 KB，还要比较脚本 Parse、Compile、Evaluate 时间，以及 LCP、Long Task、INP 和主线程占用，最终用目标市场的 RUM p75、p95 验证。

### 优化流程

```mermaid
flowchart LR
    Analyze["Bundle Analyzer<br/>定位大节点"] --> Boundary["缩小 Client Boundary"]
    Analyze --> FirstScreen["区分首屏与非首屏"]
    Analyze --> Dependency["检查依赖来源"]
    Boundary --> Split["Dynamic Import / Lazy Load"]
    FirstScreen --> Split
    Dependency --> Shake["Tree Shaking / 去重 / 子路径导入"]
    Split --> Build["比较 Route Chunk"]
    Shake --> Build
    Build --> Runtime["Parse / Evaluate / Long Task"]
    Runtime --> RUM["LCP / INP p75、p95"]
```

### 速记句

> Bundle Analyzer 找依赖来源，Network 区分公共与路由增量，Performance 和 RUM 证明体积下降真正改善体验。

## 22. 只使用组件库一个组件，为什么会打入大部分代码？

### 推荐回答

先检查组件库发布产物和消费侧依赖关系，确认打包器为什么无法静态删除未使用代码。

常见原因：

1. Barrel Import 扩大依赖图，其中某些模块有顶层注册、样式或初始化副作用。
2. 组件库发布 CommonJS，或构建阶段把 ESM 转成 `require`，导致静态分析困难。
3. `package.json` 的 `sideEffects` 配置不准确。
4. 一个看似简单的组件内部引入了完整图标库、日期库或大型子组件。
5. 同一依赖存在多个版本。
6. Server/Client 边界错误，使服务端依赖进入浏览器。

`export *` 不必然导致 Tree Shaking 失效。如果全链路是纯 ESM、没有副作用且打包器能静态分析，仍可删除未使用代码；风险通常来自 Barrel 与副作用、CommonJS、错误发布产物的组合。

处理方式包括：

- 发布保留静态 Import/Export 的 ESM 产物。
- 正确配置 Package Exports 与 `sideEffects`。
- 提供稳定子路径导入。
- 移除顶层副作用和整包导入。
- 检查依赖版本去重。
- 对支持的包使用 `optimizePackageImports` 做导入改写。

`optimizePackageImports` 是辅助优化，不能修复 CommonJS、错误副作用或不合理包结构。

### Tree Shaking 条件

```mermaid
flowchart TD
    Import["业务只导入一个组件"] --> ESM{"纯 ESM?"}
    ESM -->|No| Large["难以 Tree Shake"]
    ESM -->|Yes| Side{"副作用声明正确?"}
    Side -->|No| Large
    Side -->|Yes| Static{"导出关系可静态分析?"}
    Static -->|No| Large
    Static -->|Yes| Small["删除未使用模块"]
```

### 速记句

> Tree Shaking 依赖纯 ESM、可静态分析的导出关系和正确副作用声明；子路径导入只是手段。

## 23. 支付重复提交或重复清理，如何设计回归测试？

### 推荐回答

先把线上问题转化为业务不变量：

- 同一业务操作即使网络请求发生多次，也只能产生一个有效订单和支付结果。
- 同一逻辑操作重试必须复用幂等键。
- 同一支付记录的清理最多产生一次有效副作用。

单元测试覆盖状态机和编排：

- 重试时幂等键保持不变。
- 不同支付操作使用不同幂等键。
- Initiate、Confirm、Cancel 状态转换正确。
- 用户取消与失败回调重叠时只清理一次。
- 清理重试始终使用同一个正确 `paymentId`。
- 失败后能够恢复并安全重试。

组件测试覆盖用户可观察行为：

- 点击后按钮进入 Loading/Disabled。
- 连续点击不会重复提交。
- 支付失败显示正确反馈并清理。
- 取消与异步失败重叠时不重复删除。
- 组件卸载后迟到结果不错误更新 UI。

E2E 只覆盖关键交易闭环：订单创建、Payment Initiate、Confirm、列表刷新和 Complete 的 Happy Path，以及线上出现过的重复提交回归。第三方终端使用可控 Mock 或测试环境。

AI 可以辅助生成测试骨架、补充边界并运行最小测试，但工程师仍要 Review 业务不变量、Mock 边界和断言质量。

### 测试分层

```mermaid
flowchart TB
    E2E["E2E<br/>关键交易闭环<br/>少量高价值"]
    Component["组件测试<br/>用户交互 / 并发 / 错误反馈"]
    Unit["单元测试<br/>状态机 / 幂等 / 编排<br/>数量最多"]
    E2E --> Component --> Unit
```

### 速记句

> 单元测试保护状态机和幂等契约，组件测试保护交互与并发，E2E 保护关键交易闭环。

## 24. Cookie 登录态如何防范 XSS、CSRF 和 Token 泄漏？

### 推荐回答

XSS 是恶意 JavaScript 在当前页面上下文中执行，可能读取数据、篡改 DOM、调用接口或窃取未保护 Token。

主要防护：

- React 默认转义输出。
- 富文本白名单 Sanitization。
- 避免不安全 `innerHTML`。
- CSP 限制脚本来源。
- 第三方依赖治理。

`HttpOnly` 阻止 JavaScript 通过 `document.cookie` 读取 Token，但不能彻底解决 XSS，因为恶意脚本仍可能在当前页面调用接口。

CSRF 利用浏览器自动携带 Cookie 的特性，以已登录用户身份执行有副作用的请求。防护包括：

- `SameSite` 控制跨站 Cookie。
- CSRF Token。
- Origin/Referer 校验。
- 敏感操作鉴权与幂等。

Cookie 还应设置 `Secure`，只通过 HTTPS 发送，并缩小 Domain、Path 和有效期。

### 安全边界

```mermaid
flowchart LR
    XSS["XSS<br/>恶意脚本执行"] --> HttpOnly["HttpOnly<br/>阻止读取 Cookie"]
    XSS --> CSP["转义 / Sanitization / CSP"]
    CSRF["CSRF<br/>伪造有副作用请求"] --> SameSite["SameSite<br/>限制跨站 Cookie"]
    CSRF --> Token["CSRF Token<br/>Origin 校验"]
    Cookie["Cookie Token"] --> Secure["Secure / Domain / Path / Expiry"]
```

### 速记句

> HttpOnly 防脚本读取 Cookie，SameSite 限制跨站携带，CSRF Token 验证请求来源，CORS 管响应读取。

## 25. 为什么 CORS 不能完整防护 CSRF？

### 推荐回答

CORS 是浏览器对跨域响应读取权限的控制，不是服务端鉴权，也不是完整 CSRF 防护。

非简单请求通常先发送 OPTIONS Preflight。如果服务端不允许该 Origin，浏览器通常不会继续实际请求。但简单请求无需 Preflight，例如普通 HTML Form POST，可以直接携带符合 Cookie 策略的身份信息发送到服务端。

简单请求的典型条件：

- 方法是 `GET`、`HEAD` 或 `POST`。
- 没有非安全列表 Header。
- `Content-Type` 为 `application/x-www-form-urlencoded`、`multipart/form-data` 或 `text/plain`。

如果服务端错误地使用 GET 修改数据，攻击者还可能通过链接、图片或导航触发。即使攻击页面读不到响应，服务端副作用已经发生。

### CORS 与 CSRF

```mermaid
sequenceDiagram
    participant Evil as 攻击页面
    participant Browser as 浏览器
    participant Server as 目标服务

    Evil->>Browser: 提交简单 Form POST
    Browser->>Server: 携带符合策略的 Cookie
    Server->>Server: 执行数据修改
    Server-->>Browser: Response
    Browser--xEvil: CORS 禁止读取响应
    Note over Server: 请求副作用已经发生
```

### 速记句

> CORS 管攻击者能否读取响应，CSRF 防护管请求是否应该被执行。

## 26. 新旧系统并存时，如何保持登录态和购物车连续？

### 推荐回答

关键是让新旧系统使用同一套服务端认证和购物车身份，而不是共享 React、Redux 等运行时状态。

登录态通过 Cookie 持久化 Access Token 和 Refresh Token。只要新旧页面位于 Cookie 有效 Domain 和 Path 下，浏览器跳转时会自动携带 Cookie，两套系统都可以通过统一认证服务识别用户。

LocalStorage 按 Origin 隔离，协议、域名和端口必须一致；不同子域不能直接共享。Token 放在 LocalStorage 中也更容易被 XSS 窃取，因此更适合使用 `HttpOnly`、`Secure` 和合理 `SameSite` 的 Cookie。

旧 Cart 页面进入时，服务端读取登录 Token 和 Cart Token，再从后端获取最新购物车，以服务端为数据源，而不是依赖 PDP 的前端内存状态。

未登录用户使用 Guest Cart Token。登录后后端把游客购物车与账户购物车幂等合并，成功后再清理 Guest Token。

如果两个系统位于完全不同站点，则不能直接共享 Cookie，需要统一登录中心、一次性授权码或服务端 Token Exchange。

### 状态关系

```mermaid
flowchart LR
    Cookie["浏览器 Cookie"] --> Access["Access / Refresh Token"]
    Cookie --> Guest["Guest Cart Token"]
    Access --> New["新 Web"]
    Access --> Legacy["旧 Cart"]
    Guest --> Legacy
    New --> Backend["统一认证与购物车后端"]
    Legacy --> Backend
    Backend --> Merge["登录后幂等合并"]
```

### 速记句

> 跨系统连续性依赖共享的服务端身份与 Cookie，而不是共享前端运行时状态。

## 27. 游客购物车与账户购物车如何合并？

### 推荐回答

合并规则属于后端，前端不能自行拼接两份购物车。

登录后前端同时携带 Guest Cart Token 和 Access Token，请求后端执行合并。后端重新处理：

- 重复商品数量与最大购买限制。
- 最新价格和库存。
- 商品下架。
- 优惠券、赠品和促销冲突。
- 市场、币种和用户资格。

合并接口需要幂等，避免重复登录、刷新或多标签页同时触发时重复增加数量。

合并期间前端锁定相关操作并展示 Loading。成功后使用后端返回的完整购物车覆盖本地状态，然后清理 Guest Token；不能先清 Token，否则失败时可能丢失游客购物车。

失败时保留 Guest Token并允许安全重试。后端对价格、库存和优惠调整返回结构化结果，前端明确告诉用户哪些内容发生变化。

### 合并流程

```mermaid
sequenceDiagram
    participant Web as 前端
    participant Backend as Cart Backend
    participant Rule as Price / Stock / Promotion

    Web->>Backend: Access Token + Guest Cart Token
    Backend->>Rule: 重新计算商品、价格、库存、优惠
    Rule-->>Backend: 合并结果与调整说明
    Backend-->>Web: 完整账户购物车
    Web->>Web: 覆盖本地状态
    Web->>Web: 成功后清理 Guest Token
```

### 速记句

> 后端负责合并与重新定价，前端负责双 Token、单次触发、结果展示，并只在成功后清理 Guest Token。

## 28. API 超时、401、5xx 和业务失败如何分层处理？

### 推荐回答

重试取决于两点：错误是否可能是暂时性的，以及操作是否幂等或具备幂等键。

| 场景 | 默认处理 |
| --- | --- |
| HTTP 200 + 业务失败 | 不自动重试，提示用户修改条件 |
| 401 | 静默刷新一次，失败后重新登录 |
| 403 | 不重试，提示权限不足 |
| 429 | 遵守 `Retry-After` |
| GET + 502/503/504 | 有上限的指数退避和随机抖动 |
| 网络断开 | 等待恢复或由用户重试 |
| 支付/创建订单超时 | 查询状态或幂等重试，禁止盲目提交 |

业务失败说明请求已正常处理，重复请求通常无法改变结果。401 可以使用 Refresh Token 静默刷新，但多个并发 401 必须共享同一刷新流程。

查询类 GET 遇到临时 502/503/504 可以有限重试；写请求超时可能已在服务端成功但响应丢失，需要幂等键、状态查询或对账确认。

重试必须有次数上限、支持取消，并优先遵守服务端 `Retry-After`。

### 重试决策

```mermaid
flowchart TD
    Error["请求失败"] --> Business{"业务失败 / 4xx?"}
    Business -->|Yes| User["提示用户，不自动重试"]
    Business -->|No| Transient{"临时网络 / 502 / 503 / 504?"}
    Transient -->|No| Stop["记录并停止"]
    Transient -->|Yes| Write{"写操作?"}
    Write -->|No| Retry["有限退避重试"]
    Write -->|Yes| Idempotent{"有幂等键或状态查询?"}
    Idempotent -->|Yes| Retry
    Idempotent -->|No| Reconcile["查询最终状态 / 人工确认"]
```

### 速记句

> 重试瞬时故障，不重试业务失败；读请求通常可重试，写请求先保证幂等或确认最终状态。

## 29. 多个 401 如何避免重复 Refresh Token？

### 推荐回答

认证层维护一个全局共享的 Refresh Promise。

第一个请求收到 401 后，把认证状态切换到 Refreshing，并创建 Refresh Promise。后续请求发现刷新正在进行，不再调用刷新接口，而是等待同一个 Promise。

刷新成功后原子地更新 Access Token，等待请求分别使用新 Token 重试一次。刷新失败则统一 Reject 等待请求、清理认证状态，并只触发一次重新登录。

保护措施：

- 每个原请求最多因 401 重试一次，防止无限循环。
- Refresh 接口不进入自身的 401 Refresh 拦截。
- Refresh Token Rotation 时同一时刻只允许一次刷新。
- 重放写请求前，确认服务端在认证失败时没有执行副作用。
- 多标签页可以通过 BroadcastChannel 等机制同步 Token 和退出状态。

### Single Flight

```mermaid
sequenceDiagram
    participant A as Request A
    participant B as Request B
    participant Auth as Auth Manager
    participant Server as Server

    A->>Server: expired token
    B->>Server: expired token
    Server-->>A: 401
    Server-->>B: 401
    A->>Auth: 创建 Refresh Promise
    Auth->>Server: refresh
    B->>Auth: 等待同一个 Promise
    Server-->>Auth: new token
    Auth-->>A: retry once
    Auth-->>B: retry once
```

### 速记句

> 第一个 401 创建 Refresh Promise，其他请求共享它；成功后统一重试，失败后统一退出。

## 30. Next.js Hydration Mismatch 如何定位与避免？

### 推荐回答

Hydration Mismatch 的本质是服务端 HTML 与客户端第一次 Render 期望的内容或结构不一致。

常见原因：

- `Date.now()`、`Math.random()` 等非确定值。
- Locale、Timezone、Market、Currency 不一致。
- 首次 Render 读取 Window、LocalStorage、屏幕尺寸或媒体查询。
- 服务端和客户端登录态、Feature Flag 或缓存数据不同。
- 在 Render 中根据 `typeof window` 输出不同 DOM。
- 非法 HTML 嵌套被浏览器自动修正。
- 第三方脚本或浏览器扩展提前修改 DOM。

定位时查看 Next Error Overlay 和控制台节点路径，对比服务器 HTML 与 Hydration 后 DOM，寻找第一个差异节点。只在部分用户出现时，检查扩展、时区、语言、市场和实验配置。

避免方式：

- 第一次 Render 使用确定输入。
- Locale、Timezone 等由服务端计算并通过 Props 传递。
- 客户端专属数据先使用稳定占位，在 `useEffect` 后更新。
- 浏览器专属第三方组件缩小 Client Boundary，必要时关闭 SSR。
- 保持合法 HTML。
- `suppressHydrationWarning` 只用于确实无法一致的局部文本。

### 排查图

```mermaid
flowchart TD
    Error["Hydration Mismatch"] --> Compare["比较 Server HTML 与首次 Client Render"]
    Compare --> Value["时间 / 随机值"]
    Compare --> Env["Locale / Timezone / Market"]
    Compare --> Browser["Window / LocalStorage / Media"]
    Compare --> HTML["非法 HTML 嵌套"]
    Compare --> Third["脚本或扩展修改 DOM"]
    Value --> Deterministic["改为确定输入"]
    Env --> Props["服务端统一后通过 Props 传递"]
    Browser --> Effect["挂载后再更新"]
    HTML --> Fix["修正语义结构"]
    Third --> Isolate["隔离第三方组件"]
```

### 速记句

> Hydration 的第一次客户端 Render 必须复现服务端 HTML；浏览器专属差异放到挂载后处理。

## 31. Next.js Middleware 适合处理什么？

### 推荐回答

Middleware 位于用户请求和 Route 之间。在当前项目的 Next.js 14 环境中使用 Edge Runtime，适合简单、确定、低延迟的入口判断。

适合：

- 根据 Host 或 URL 解析 Market、Region、Locale。
- Redirect 与 Rewrite。
- 读取 Cookie，判断基础登录状态。
- 向下游补充语言、市场 Header。
- 设置语言、地区 Cookie。
- 维护模式和简单访问控制。

不适合：

- 复杂业务编排和大量状态计算。
- 数据库查询或多个串行 API。
- 大型第三方 SDK 或依赖 Node.js API 的包。
- 支付、购物车等长事务。
- 可以下沉到 Route、Server Component 或后端的重型认证逻辑。

Middleware 位于所有匹配请求的关键路径，额外延迟会直接影响 TTFB。应通过 Matcher 排除图片、字体、JavaScript Chunk、健康检查等静态资源。

可观测性只记录轻量结构化日志，不在 Edge Middleware 中初始化复杂 Sentry Capture 或 Trace。

### 请求链路

```mermaid
flowchart LR
    Request["用户请求"] --> Match{"Matcher 命中?"}
    Match -->|No| Route["直接进入资源或 Route"]
    Match -->|Yes| Middleware["解析 Market / Locale / Cookie"]
    Middleware --> Decision{"Rewrite / Redirect?"}
    Decision -->|Yes| Target["目标地址"]
    Decision -->|No| Header["补充 Header 后继续"]
    Header --> Route
```

### 速记句

> Middleware 只处理入口处的轻量横切逻辑；复杂业务和远程 I/O 下沉到 Route、Server Component 或后端。

17. API 重试：瞬时故障可重试，业务失败不重试，写请求先保证幂等。
18. Refresh：多个 401 共享一个 Refresh Promise。
19. Hydration：首次客户端 Render 必须复现服务端 HTML。
20. Middleware：只放轻量入口逻辑，复杂 I/O 下沉。
