# 多店铺主题 Monorepo 架构设计：共享工程流程，独立交付店铺

同一个开发者维护两套电商主题时，最危险的错误往往能通过编译：改的是 A 店的购物车，预览用的却是 B 店的数据；代码在本机正确，上传时覆盖了运营刚调好的首页。把两个项目移进同一个仓库，可以统一检查和交付方法，却不会自动解决这两类问题。

这份设计给每次构建绑定一个明确的店铺，并让交付记录能回答三个问题：这批文件来自哪里，要写到哪个主题，怎样证明写入后仍保留了独立修改？

## 一、共享哪些东西

| 层次 | 共享的内容 | 保持独立的内容 |
| --- | --- | --- |
| 工程流程 | 任务入口、配置校验、构建清单、差异比较、验收方式 | 各店的业务需求、设计依据与验收范围 |
| 主题应用 | 相同的构建与验证约定 | 主题模板、业务组件、样式、依赖锁、预览端口 |
| 基础能力 | 监控运行库、埋点运行时 | 各店的事件契约、初始化入口、运行时开关 |
| 环境与交付 | 凭据加载规则和目标核验方法 | 店铺凭据、草稿主题、产物和发布授权 |

例如，两家店可以调用相同的监控库。某家店的购物车事件、商品参数或设计尺寸不应因此成为公共库的默认值。根任务负责编排，应用仍按自己的锁文件安装依赖；合仓不要求两套主题同时升级，也不要求抽出公共业务组件。

## 二、先确定应用，再读取配置

每个任务从显式的应用标识开始。解析器据此返回店铺、源码位置、产物位置、预览尺寸与交付策略，并检查它们是否属于同一应用。传入 A 店标识、配置却指向 B 店时，直接停止。命令行上一次访问的店铺不能补齐缺失配置。

凭据也跟随应用。缺少凭据时，静态组件仍可预览；需要真实商品数据的检查则报告缺失。不要从另一个应用借用同名变量，否则一次看似成功的预览就可能掩盖串店。

## 三、用内容清单识别候选版本

一次主题构建复制平台支持的主题文件，再编译已登记的监控和埋点入口。生成脚本、锁文件和共享源码都是构建输入。构建开始时将旧候选标记为失效，结束时计算输入和输出的内容哈希，检查构建期间是否发生变化。供错误定位使用的源码映射保存在交付包之外。

```mermaid
flowchart LR
  A[选择店铺应用] --> B[校验配置与依赖]
  B --> C[复制主题并编译登记的脚本]
  C --> D[记录文件清单与内容哈希]
  D --> E[比较远端草稿]
  E --> F[写入获准的差异并回读]
```

Git 提交号能定位提交，不能标识未提交的修改。例如，开发者在构建后又改了一行事件映射，此时提交号可能没变，但输入哈希已经变化。这种情况应重新构建，不能拿上一次生成的脚本去验证这次改动。

## 四、为什么需要两次合并

线上主题可能有运营编辑，目标草稿也可能有尚未发布的实验。仅比较本地分支与线上版本，会漏掉草稿独有的修改。可以将交付分两步：

```text
第一步：以已接受的线上版本为共同祖先，合并本地修改和当前线上修改。
第二步：以上次已验证的目标草稿为共同祖先，将第一步的结果与当前草稿合并。
写入计划：比较当前草稿与第二步的结果，只列出实际需要写入的文件。
```

设想开发者修了商品卡片，运营同时换了首页横幅，草稿中还保留着下一场活动的布局。卡片修复有清晰归属，可以正常进入候选；两个版本的首页配置则需要逐项判断。不能仅凭文件时间较新就选中其中一份。缺少共同祖先，或写入前发现草稿再次变化时，应重新取数和比较。

## 五、完整比较，有限写入

比较要覆盖完整主题，才能看到目标独有文件和间接依赖；写入只包括此次授权的差异及必要依赖。目标独有文件默认保留。写入前核对店铺、主题身份、主题角色以及拟写文件的当前内容，写入后逐项回读并比对哈希。

验收结果也要分开记录：本地构建通过说明候选能生成；组件预览通过说明样例数据下的交互符合预期；远端文件回读一致说明目标收到了这些文件。真实店铺的数据、平台渲染和用户操作仍需单独验证。某个文件回读失败时，保留本次尝试及差异，不把整个草稿登记为新的成功基线。

这套设计的取舍是多维护一份候选清单和两份可追溯基线。它换来的是具体的交付判断：哪些改动可以写，哪些要留给运营，哪些因为证据不足必须先停下来。
