# 交易模块可观测性技术方案

## 1. 背景与目标

交易链路是 Joyboy 最关键的业务闭环。本方案为 checkout/payment 建立统一的事件模型、字段协议与可视化 / 告警口径。

目标不是重建监控体系，而是在现有 Sentry + `@castlery/observability` 的基础上：

* 让团队能按阶段观察 checkout 与 payment 的转化漏斗。
* 让故障定位从「人工翻日志」收敛为「按 `txn_trace_id` / `orderId` / `paymentId` 关联检索」。
* 让交易异常能区分系统故障、业务失败、用户可恢复错误与第三方波动。
* 让告警基于 SLI/SLO，而非仅依赖单点 exception 数量。
* 发布后 30 分钟内能判断是否引入交易成功率回归。

## 2. 设计目标

### 2.1 业务目标

* 按阶段观察 checkout / payment 转化漏斗。
* 故障定位收敛为「按 id 关联检索」。
* 区分系统故障 / 业务失败 / 用户可恢复错误 / 第三方波动。
* 告警基于 SLI/SLO。
* 发布 30 分钟内可判断回归。

### 2.2 技术目标

* **统一字段标准**：Sentry tag、Prometheus label、Loki field、Tempo span attribute 使用一致的上下文模型（camelCase 上下文 → snake_case 发射，见 `transaction-instrumentation-spec.md`）。
* **统一链路关联**：同一笔交易以业务伞状 ID `txn_trace_id` 贯穿，并可用 `orderId`、`paymentId` 关联；OTel 技术 `trace_id`（前端采集 `X-Request-Id`）为 per-request 通道，两层并存（见 `transaction-instrumentation-spec.md` §10）。
* **统一分层职责**：Sentry 看异常与 root cause，Grafana 看指标、趋势、日志、trace、告警与 SLO。
* **统一采样策略**：关键交易链路高采样，失败交易全量保留错误上下文。
* **统一安全边界**：禁止上报支付敏感信息与完整 PII（§5.3）。

## 3. 平台职责划分

> 一句话：**Sentry 看「为什么失败」，Grafana 看「影响有多大、从哪里继续查」。**

| 问题类型 | 优先平台 | 典型场景 |
| --- | --- | --- |
| 代码异常 / Root Cause | Sentry | `capturePaymentAction` 抛错、SDK 初始化失败 |
| 业务成功率下降 | Grafana + Prometheus | 某 provider 支付成功率从 96% → 72% |
| 日志回溯 | Grafana + Loki | 按 `txn_trace_id` / `order_id` 查结构化日志（OTel `trace_id` 钻取单 request trace） |
| 服务端调用链 | Grafana + Tempo | Server Action → PaymentService → Backend API span |
| 发布回归 | Grafana | 某版本上线后 p95 latency 翻倍 |
| 跨版本 / 市场趋势 | Grafana | 多版本、多 region 成功率对比 |

**基本原则**：

* 错误与根因优先进 Sentry。
* 指标、漏斗、趋势、日志查询与告警优先进 Grafana。
* 关键业务节点同时写结构化日志与业务 metric。
* 同一交易链路必须能在 Sentry 与 Grafana 之间互相定位（靠业务 `txn_trace_id`）。
* 不再使用 Datadog 作为任何交易监控依赖。

## 4. 交易链路观测模型

### 4.1 标准阶段（step）

所有埋点、日志、错误、指标都必须挂靠到某一个标准阶段。枚举以 `libs/shared/observability/src/lib/transaction-observability/types.ts` 为单一事实源；下表按**标准执行顺序**（同一笔交易的时间先后）排列：

| Step Index | Step（types.ts 枚举值） | 说明 | 执行侧 | 状态 |
| --- | --- | --- | --- | --- |
| 1 | `checkout_init` | 进入 checkout 页面 | 客户端 |  |
| 2 | `checkout_info_fetch` | 拉取 checkout / quote / order info | 客户端 |  |
| 3 | `address_validate` | 地址与配送校验 | 客户端 |  |
| 4 | `confirm_shipping` | 完成配送服务确认 | 客户端 |  |
| 5 | `inventory_reserve` | 库存预占 | 服务端 |  |
| 6 | `payment_method_select` | 选择支付方式 | 客户端 |  |
| 7 | `payment_sdk_ready` | 第三方 SDK 初始化完成 | 客户端 |  |
| 8 | `create_order` | 创建交易订单 | 客户端直调 | 核心 |
| 9 | `payment_initiate` | 创建 payment intent / transaction | Server Action → 支付域 | 核心 |
| 10 | `payment_sdk_submit` / `payment_popup` / `payment_redirect` | **同一逻辑步骤「发起支付动作」**，按支付方式择一：提交 / popup / 跳转 | 客户端 |  |
| 11 | `payment_sdk_confirm` | **Optional** SDK 接收到第三方的支付成功回调时触发 | 客户端 | **部分支付方式，前端无法追踪该步骤。比如进入第三方支付页面/弹窗支付的场景，由第三方 confirm** |
| 12 | `payment_callback_receive` / `payment_capture` | 回调到达 → capture / finalize payment（同一逻辑步骤） | Callback Route / Server Action → 支付域 | 核心（capture） |
| 13 | `payment_result_render` | 成功 / 失败页渲染 | 客户端 | 枚举已定义，代码未发射 |

> **顺序与分组说明**：
>
> * **Step 10 / Step 12 是文档分组**：多个枚举值代表「同一逻辑步骤、不同支付方式表现不同」（Step 10 发起支付动作：ZipPay/GrabPay 走 redirect、PayPal 走 popup；Step 12 回调到达 → capture），`types.ts` 仍保留为各自独立枚举值，**不合并枚举**（仅展示与口径上视为同一步）。
> * **Step 11** `payment_sdk_confirm` **是面向所有支付方式的通用「SDK 确认」步骤**：部分方式（跳第三方页 / 弹窗）由第三方 confirm、前端无法追踪；Stripe 的 `stripe.confirmPayment` 只是该通用步骤的具体落点之一（见 `transaction-instrumentation-spec.md` §9）。

> **核心三步**（SLO / 首批告警 / 首批 dashboard 优先覆盖）：`create_order`、`payment_initiate`、`payment_capture`。

> **代码现状对齐**：截至目前实际已发射的 step 为`payment_method_select`、 `create_order`、`payment_initiate`、`payment_sdk_ready`、`payment_sdk_confirm`、`payment_redirect`、`payment_popup`、`payment_capture`、`payment_callback_receive`（见 `libs/modules/payment/actions/.../payment.action.ts`、`.../payment-wallets/hooks/use-payment-execution.ts`、`.../utils/capture-with-retry.ts`、`apps/web/.../checkout/{zippay,grabpay}/page.tsx`）。`payment_result_render`在/checkout/success page 执行；见 `transaction-instrumentation-spec.md` §9。

### 4.2 标准结果态（result）

`success` / `failure` / `timeout` / `canceled` / `processing` / `retrying`（外加起始态 `started`）。枚举值以 `types.ts` 的 `TransactionResult` 为准。

### 4.3 错误分类（errorCategory）

`system_error` / `provider_error` / `network_error` / `validation_error` / `business_rule_error` / `timeout_error` / `user_abort` / `unknown_error`。

> 作用：避免把库存变化、优惠券失效、用户取消支付，全部误当成 P1 系统故障。`business_rule_error` 与 `user_abort` 默认 `skipSentry`，只进日志 / metric。

## 5. 统一字段规范

字段字典、命名规则、各信号的映射（Sentry tag / Prometheus label / Loki field / Tempo span attribute）见 `transaction-instrumentation-spec.md`。这里只给要点。

### 5.1 必备字段

`domain`、`step`、`result`、`traceId`、`attemptId`、`orderId`、`orderNumber`、`paymentId`、`provider`、`region`、`locale`、`env`、`service`、`version`、`release`。

### 5.2 推荐业务字段

`cartId`、`checkoutTokenHash`、`currency`、`paymentAmount`、`paymentMethodKey`、`retryCount`、`httpStatus`、`errorCode`、`is3DS`、`isRedirectFlow`、`isFallbackFlow`。

### 5.3 安全边界

**禁止上报**：

* 卡号 / CVV / 完整账单地址
* 完整邮箱 / 手机号 / 姓名
* provider 原始 payload
* 完整 checkout token / client secret
* 任何可逆支付凭证

**允许上报**：

* ID / 枚举 / 状态码 / 归类后的错误码
* token 的 hash 或脱敏形式
* 区间化金额
* 市场 / provider / 版本 / 阶段 / 结果

## 6. 发射路径设计（OTel SDK 接入）

> 这是本版方案补齐的核心缺口。完整细节见 `otel-integration-spec.md`，这里给整体形状。

```
                    ┌──────────────── 浏览器 (Web App) ────────────────┐
                    │  OTel Web SDK：交易 span + transaction metrics    │
                    │  传播：traceparent / tracestate / baggage         │
                    └───────────────┬──────────────────────────────────┘
                                    │ OTLP/HTTP
                                    ▼
            ┌────────────── OpenTelemetry Collector ──────────────┐
            │  接收 OTLP → 处理（batch / 脱敏 / 资源标签）→ 导出    │
            └───────┬───────────────────────┬──────────────────────┘
                    │ traces                 │ metrics
                    ▼                        ▼
                  Tempo                 Prometheus / Mimir
                    │                        │
   服务端日志 (pino JSON, 含 trace_id + txn_trace_id) ──► Loki
                    │                        │
                    └────────────┬───────────┘
                                 ▼
                              Grafana  （Dashboard / Alerting / SLO）

   错误与根因 ──► Sentry（独立通道，靠业务 txn_trace_id 与上面四者互相定位）
```

设计要点（详见 OTel 接入实践）：

1. **前端 OTel 职责收敛**：只埋交易关键阶段 span + 4 条 transaction metrics，不做通用浏览器自动 instrumentation（避免噪音，与 milestone「客户端体验指标 out of scope」一致）。
2. **导出走 Collector**：浏览器经 OTLP/HTTP → Collector（避免直连后端的 CORS / endpoint / 鉴权复杂度，并由 Collector 统一 batch、脱敏、打资源标签）。
3. **服务端 trace 由 Node OTel 产生**：Server Action → PaymentService → ProviderStrategy → Backend API 形成跨服务 trace。
4. **关联约束（硬要求）**：OTel `service.name` 必须与 Loki `service` 标签一致，否则 Tempo → Loki 关联会断（见 `otel-integration-spec.md` §7）；服务端日志必须同时输出 OTel `trace_id`（per-request）与业务 `txn_trace_id`（per-transaction-flow）。
5. **两层 trace + 与 Sentry 共存（方案 A）**：

    * 业务伞状 ID 出口统一 `txn_trace_id`（Sentry tag / Loki / Tempo `transaction.txn_trace_id`），前端透传 header `x-txn-trace-id`，贯穿整笔交易。
    * OTel 技术 `trace_id` 走 W3C `traceparent` / `tracestate`，per-request；前端通过响应头 `X-Request-Id` 采集做弱关联（后端 continue 列为下一步）。
    * Sentry tracing 继续走 `sentry-trace` + `baggage`，**保留不动**（后端目前未消费）。
    * 详见 `transaction-instrumentation-spec.md` §10.6 / §10.8。

6. `transaction-observability` **helper 扩成多出口**：在现有「Sentry + logger」基础上增加 OTel span/metric 出口（新增 `otel.ts`），业务侧调用方式不变。

> **中间件 / Edge 约束**：遵守 CLAUDE.md 硬规则——中间件 / Edge runtime 不做 Sentry capture，也不在其中起 OTel tracing；`logger.*` 允许（仅写 stdout）。

## 7. Sentry 设计方案

### 7.1 与当前实现对齐

* 客户端初始化：`apps/web/instrumentation-client.ts`（`beforeSend` 先 `classifyErrorBucket` 写 `error_bucket` / `bucket_confidence`，再过滤噪音）。
* 服务端 / Edge：`apps/web/instrumentation.js` 分别调用 `sentry.server.config.ts` / `sentry.edge.config.ts` 的 `initSentry()`。
* 业务侧错误统一通过 `@castlery/observability` 的 `captureStructuredError` / transaction helper，**不直接散写** `Sentry.captureException`。

### 7.2 Scope 与 Tag 规范

交易异常捕获前统一设置：`domain` / `step` / `provider` / `region` / `result` / `errorCategory` / `orderId` / `paymentId` / `traceId`（**出口 Sentry tag** `txn_trace_id`）/ `attemptId` / `release`。

`@castlery/observability` 已提供交易 helper，业务侧复用即可：`trackTransactionStart/Success/Failure/Timeout`、`captureTransactionError`、`reportTransactionMessage`、`addTransactionBreadcrumb`。

### 7.3 Breadcrumb 与采样

* Breadcrumb 只记录高价值节点：`checkout page entered`、`payment method selected`、`order created`、`payment initiated`、`3DS started`、`redirect returned`、`capture succeeded`。
* 采样：普通页面 0.1% ~ 1%、 checkout/payment 页面 ~20%、失败交易 100%、新支付方式上线窗口临时 20% ~ 50%；优先用 `tracesSampler` 动态决策。

### 7.4 checkout / payment 基础设施 —— 预留契约（BLOCKED）

> **状态：blocked。** CLAUDE.md 硬规则明确「Checkout / Payment / Cart 模块尚未兼容完成，兼容完成前禁止新增 Sentry instrumentation」。本节按**接口契约**预留，迁移完成后再接入，**当前不落地 page 级 context 代码**。

预留内容（详见 `sentry-transaction-spec.md`）：

* 每个交易 `page.tsx` 将调用 `setGlobalSentryContext({ pageType, domain })`（迁移后接入）。
* layout 使用 `SentryContextProvider`（迁移后接入；当前 cart route 的 placeholder 不视为已完成）。
* 交易错误观测（`captureTransactionError` / breadcrumb）这一半**不依赖** page 级 context，可随 OTel 接入先行落地——payment 主链路实际已在用。

## 8. Grafana 设计方案

详见 `grafana-dashboard-spec.md` 与 `grafana-alerting-slo-spec.md`。要点：

* **Metrics（4 条）**：`transaction_step_total`、`transaction_step_duration_seconds`、`transaction_retry_total`、`transaction_callback_total`。低基数 label：`env, service, version, domain, step, result, provider, region, error_category`。`txn_trace_id` / `trace_id` / `order_id` / `payment_id` **禁止**做 metric label（进 Loki / Tempo）。
* **Dashboard（4 个）**：`Transaction Overview`、`Provider Drilldown`、`Release Regression`、`Region Health`，统一过滤变量 `env, service, version, region, provider, step, result`。
* **SLO（30 天窗口）**：`create_order` ≥ 99.5%、`payment_initiate` ≥ 99.0%、`payment_capture` ≥ 98.5%，按 provider 拆分覆盖实际活跃支付方式：`stripe-online`、`stripe-link-pay`（Express）、`grabpay`、`zippay`、`2c2p`、`paypal-online`、`affirm`。
* **告警**：失败率静态阈值（5 分钟窗口、最小样本 20）+ 双窗口 burn rate；发布窗口加严阈值。告警 message 带 dashboard / Loki query / runbook / Sentry search 链接。

## 9. 埋点落点建议

* **Client**：checkout 进入、地址提交、优惠券应用、支付方式切换、submit 点击、SDK ready/confirm/redirect/popup、成功 / 失败页渲染。
* **Server**：create order、initiate payment、capture payment、callback / webhook、retry / fallback / rollback、provider adapter 异常与耗时。
* **Provider 适配层**：每个 provider 统一输出 request start / success / failure / timeout / retry / final result，收敛在 strategy / service 层，不散落在页面组件。

## 10. 分阶段落地计划

| Phase | 内容 | 关键产出 |
| --- | --- | --- |
| **P1 标准与字段** | 固化 step / result / errorCategory 枚举、字段字典、`traceId` / `attemptId` 生成与透传、PII 脱敏规范、平台分工 | `transaction-instrumentation-spec.md` |
| **P2 OTel 接入** | 集成 OTel Web SDK + Node SDK，配置 Collector / OTLP exporter，`service.name` 与 Loki 对齐，`transaction-observability` 增 OTel 出口 | `otel-integration-spec.md` |
| **P3 Datadog 下线** | 移除 `@datadog/browser-rum` / `dd-trace` 依赖、`datadog-init.tsx` ×2、`instrumentation.js` 内 `tracer.init()`、DD env | §11 清单 |
| **P4 核心链路接入** | `create_order` / `payment_initiate` / `payment_capture` / redirect callback / 成功失败页 的 metric + log + trace | payment 主链路已大部分接入，补 OTel 出口验证 |
| **P5 可视化与告警** | 建 4 个 Dashboard、3 条 SLO、核心告警 + burn rate、release regression 视图 | Grafana 规格文档 |
| **P6 治理与扩展** | provider 逐个补齐、噪音过滤、Sentry checkout/payment 基础设施（待 blocked 解除）、runbook 与 oncall 流程 | `runbook.md` |

> 顺序原则：**先确认 Grafana 数据源字段可检索（OTel → Tempo/Prometheus、日志 → Loki），再建 Dashboard / Alert**；否则字段不稳定会导致后续返工。

## 11. Datadog 全量下线清单

本方案前提是「不再使用 Datadog」。除 `transaction-observability` 模块内已解耦外，应用层下线纳入 P3：

| 位置 | 当前内容 | 处理 |
| --- | --- | --- |
| `package.json` | `@datadog/browser-rum`、`dd-trace` 依赖 | 移除 |
| `apps/web/app/datadog-init.tsx` | `datadogRum.init()` 客户端 RUM | 删除 |
| `apps/pos/app/datadog-init.tsx` | POS 客户端 RUM | 删除 |
| `apps/web/app/layout.tsx` | 引入 `DatadogInit` | 移除引用 |
| `apps/web/instrumentation.js` | `dd-trace` `tracer.init()`（logInjection / runtimeMetrics / HTTP blocklist） | 替换为 OTel Node SDK 初始化（见 OTel 接入实践） |
| `libs/config/src/ec-env.ts` | `NEXT_PUBLIC_DATADOG_APP_ID` / `NEXT_PUBLIC_DATADOG_CLIENT_TOKEN` | 移除 |

> `instrumentation.js` 里 dd-trace 当前承担「服务端自动 trace + log 注入 trace_id」。下线时必须由 OTel Node SDK 顶上，否则会丢服务端 trace 与日志 `trace_id` 关联——这是 P2 与 P3 必须连做的原因。

## 12. 成功标准

* 能按业务 `txn_trace_id` 串起一次交易的前端动作、服务端日志、Tempo trace 与 Sentry 异常。
* 能按 `provider` / `region` / `version` 快速判断影响面。
* `payment_capture` 失败可在 5 分钟内被发现。
* 交易异常能区分系统故障与业务失败，减少无效告警。
* 发布后 30 分钟内可通过 Grafana Dashboard 判断是否回归。
* 从 Grafana alert 能跳转到对应 dashboard、Loki 查询、Tempo trace 与 Sentry issue search。
* 仓库内**零 Datadog 残留**（依赖 / 初始化 / env）。
