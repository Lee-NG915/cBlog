## 2. helper API

| --- | --- | --- |
| `trackTransactionStart(ctx, opts?)` | 阶段开始 | log + breadcrumb + OTel span start + `transaction_step_total{result=started}` |

## 3. 枚举（以 types.ts 为准）

* **TransactionDomain**：`checkout` | `payment`
* **TransactionStep**：`types.ts` 现有 16 个枚举值，按标准执行顺序排列并分组展示见 `README.md` §4.1。几个易混淆点：

    * `payment_sdk_submit` / `payment_popup` / `payment_redirect`（发起支付动作）、`payment_callback_receive` / `payment_capture`：各为「同一逻辑步骤、不同支付方式表现」的文档分组（枚举不合并）。
    * `payment_sdk_confirm`：面向所有支付方式的通用「SDK 确认」步骤（Stripe 的 `confirmPayment` 为其落点之一）。
    * `payment_result_render`：枚举已定义但代码未发射。

* **TransactionResult**：`started` | `success` | `failure` | `timeout` | `canceled` | `processing` | `retrying`（注意 `canceled` 单 `l`）
* **TransactionActionType**：`SDK_CONFIRM` | `REDIRECT` | `SDK_POPUP` | `SUCCESS`（与 `payment.strategy.ts` 的 `ActionSchema` 对应）
* **TransactionErrorCategory**：`system_error` | `provider_error` | `network_error` | `validation_error` | `business_rule_error` | `timeout_error` | `user_abort` | `unknown_error`

新增 / 修改枚举值必须改 `types.ts`（单一事实源），并同步本文与 Grafana 规格的口径。

## 5. 信号映射（关键）

同一份 `TransactionObservabilityContext`（camelCase）映射到 4 个出口，**命名风格在出口处统一为 snake_case**，避免 Loki / Prometheus 字段分裂。

| 上下文字段 | Sentry tag | Prometheus label | Loki field | Tempo span attribute |
| --- | --- | --- | --- | --- |
| `domain` | `domain` | `domain` | `domain` | `transaction.domain` |
| `step` | `step` | `step` | `step` | `transaction.step` |
| `result` | `result` | `result` | `result` | `transaction.result` |
| `provider` | `provider` | `provider` | `provider` | `transaction.provider` |
| `region` | `region` | `region` | `region` | `transaction.region` |
| `errorCategory` | `errorCategory` | `error_category` | `error_category` | `transaction.error_category` |
| `errorCode` | `errorCode` | ❌（高基数禁用） | `error_code` | `transaction.error_code` |
| `version` | `release` | `version` | `version` | `service.version` |
| `env` / `service` | tag | `env` / `service` | `env` / `service` | resource attr |
| `traceId`（业务伞状 ID） | tag `txn_trace_id` | ❌ | `txn_trace_id` | `transaction.txn_trace_id` |
| `attemptId` | tag `attemptId` | ❌ | `attempt_id` | `transaction.attempt_id` |
| `orderId` | tag `orderId` | ❌ | `order_id` | `transaction.order_id` |
| `paymentId` | tag `paymentId` | ❌ | `payment_id` | `transaction.payment_id` |

**命名约定**：业务伞状 ID 的 context 字段保持 camelCase `traceId`（`types.ts` 单一事实源不变），但**所有出口统一命名** `txn_trace_id`——故意不用常规的 `trace_id`，把 `trace_id` 让给 OTel span 的技术 trace（见 §7、§10.6）。两者语义不同、在 Loki 同时存在、互不覆盖、可联查。

**铁律**：`txn_trace_id` / `order_id` / `payment_id` / `attempt_id` / `error_code` **绝不**作为 metric label（高基数会撑爆 Prometheus）；它们只进 Loki field 与 Tempo span attribute，用于按 id 回溯。

## 7. Loki 日志字段

服务端交易日志统一 JSON，保证以下字段稳定可检索：

`service`、`env`、`version`、`level`、`message`、`domain`、`step`、`result`、`provider`、`region`、`txn_trace_id`、`trace_id`、`attempt_id`、`order_id`、`payment_id`、`error_code`、`error_category`。

**两个 trace 字段并存**：

* `txn_trace_id` — **业务伞状 ID**，贯穿整笔交易（init checkout → payment result），由**前端生成**、跨页/跨回跳存活（见 §10）。用于按一笔交易回溯全链路。
* `trace_id` — **OTel/Tempo 技术 trace**，由**后端生成**（每个 request 一个），per-request、跨步骤即变。后端日志侧由 logger 从 active span 注入；**前端侧通过采集响应头** `X-Request-Id` **获得**（见 §10.8）。用于单次 request 内 client↔server↔Tempo 联查。

两者语义不同、互不覆盖。字段名稳定、全小写 snake_case，禁止 camelCase / snake_case 混用。

### 9.1 关键事实

* **create_order 是 RTK Query mutation**（BFF `/api/v1/order/create`，带 `X_CHECKOUT_TOKEN` header，`maxRetries:0`），**不是 Server Action**；失败由 `CheckoutProcessFailedEvent` Redux listener 处理。
* **Server Action 只有两个**：`initiatePaymentAction` / `capturePaymentAction`（`@castlery/modules-payment-actions`）。抛错路径用 `withServerActionInstrumentation`；优雅降级（`return {}`）用 `captureStructuredError`（CLAUDE.md 硬规则）。
* **provider strategy 层**（`payment.strategy.ts`）：`ActionSchema` 决定动作类型——`SDK_CONFIRM`（Stripe）/ `REDIRECT`（ZipPay、GrabPay、**2C2P**、Affirm）/ `SDK_POPUP`（PayPal、Affirm popup）/ `SUCCESS`。provider 专有错误码映射到统一 `errorCategory`。
* **capture 重试**：`capture-with-retry.ts` 指数退避，发 `RETRYING` / `TIMEOUT` 消息，喂 `transaction_retry_total`。

### 9.2 Redirect callback

* 事件顺序：`payment_redirect`（发起）→ `payment_callback_receive`（回跳页）→ `payment_capture` → `payment_result_render`（待补）。
* **统一回调入口（已在 strategy 层落地）**：四个 REDIRECT strategy 的 `returnUrl` 已统一指向 `/{country}/checkout/payment-callback?provider=<key>`（`key` = `grabpay` / `zippay` / `2c2p` / `affirm`，取自 `PaymentMethodProviderEnum`，单一事实源）。第三方回跳时在其后追加自身参数（如 GrabPay 的 `&grabTxID=&partnerTxID=`），与 `?provider=` 自然组合。
* **统一回调页（待实现）**：`apps/web/.../checkout/payment-callback/page.tsx` —— 按 `provider` query 派发到 **per-provider 解析注册表**（`{ [provider]: parseCallback }`，与 domain strategy 模式对称）→ 还原上下文 → `capturePayment` → 按结果 redirect（success / payment-resume）。**建议用** `route.ts`**（Route Handler）而非 page**：无 UI、且 2C2P 等可能 `form_post` POST 回跳，route handler 能接 POST。
* **可观测性落点**：`payment_callback_receive` 埋点**只在统一页发射一次**，用 `provider` 字段区分来源。新增 redirect provider = 注册表加一项，不新增页、不新增埋点点位。
* 时序见 `diagrams.md` §3。

**回跳 query 校验**：部分 provider 要求 returnUrl 预注册或会裁剪 query。统一为单一 URL 反而**更易登记**，但 `?provider=` 判别器必须在整圈回跳后存活——需逐 provider 验证（与后端/provider 配置对齐回跳模式 GET/POST 与参数保留）。

待补埋点：`payment_result_render`（成功/失败/processing 页渲染）、`payment_method_select` 全量化。补齐前，dashboard 中 `payment_result_render.*` 面板无数据。

## 10. `traceId` 全程贯穿：生命周期与传播

**命名对齐**：调研文档（`frontend-transaction-monitoring-research.md` §5）中的 `txn_trace_id` 即本文 §4.1 的 context 字段 `traceId`——context 保持 camelCase `traceId`，**所有出口统一命名** `txn_trace_id`（方案 A，见 §5 / §10.6）。本节解决「这个 ID 怎么生成、怎么在跨页 / 跨 server-client / 跨第三方网关回跳中存活、怎么传播」的细则——`types.ts` 只定义字段，不定义生命周期。

### 10.1 为什么需要一个业务层贯穿 ID（而非依赖 OTel / Sentry 原生 trace）

平台原生 trace 解决的是「一次 trace 内」的 client↔server 串联，但交易链路有三个天然断裂点：

1. **跨页面导航** — init checkout / create order / payment 多为不同 page / request，每进新页默认开新 trace，原生 trace id 即变。
2. **server/client 边界 + 多次往返** — 一条 OTel trace 撑不住几分钟、多步骤的漏斗。
3. **跳转第三方支付网关再回跳** — 离开域名瞬间 JS 上下文与内存态全断，回跳后「失忆」。

因此 `traceId` 是**业务层伞状相关性 ID**，与 OTel span trace_id（技术层、per-trace）**互补共存**，不是替代关系。

### 10.2 ID 模型（伞状）

```
traceId  (前端生成 UUID，一笔交易内全程不变)
  ├── attemptId        ← 每次发起支付生成（一笔交易可多次 attempt）
  ├── checkoutTokenHash← init checkout 阶段附加（脱敏）
  ├── orderId / orderNumber ← create order 成功后附加
  └── paymentId        ← payment initiate 成功后附加
```

`traceId` 是「伞」，其余 ID 是沿途挂上去的**属性**。给定任意属性都能反查回 `traceId`，再展开完整时间线。

### 10.3 生命周期（状态机）

```
[无] --进入 checkout（init checkout 第一步）--> 生成 traceId
        │  (幂等：当前会话已存在则复用，绝不一笔交易多 ID)
        │
        ├─ create order success   → 挂 orderId / orderNumber
        ├─ payment initiate        → 生成 attemptId、挂 paymentId
        ├─ 跳转网关 / 回跳           → 依赖 cookie 存活（见 10.4）
        ├─ 支付重试                 → traceId 不变，attemptId 递增
        │
        └─ payment result 终态（success / 终态 failure / canceled）
                                    → 清理 traceId，下次结算重新生成
```

* **不变量**：一笔交易（从 init checkout 到 payment result）`traceId` 唯一且不变；重试只变 `attemptId`。
* **幂等生成**：读 → 有则复用、无则生成，避免并发 / 多 tab 产生多个 ID。

### 10.4 持久化与「回跳黑洞」存活（关键）

| 载体 | 作用 | 失效场景 |
| --- | --- | --- |
| 内存（Redux / context） | 当前页快速读写 | 页面刷新 / 导航即丢 |
| `sessionStorage` | 扛 tab 内页面跳转、刷新 | 跨 tab、跳出域名回跳可能丢 |
| **Cookie** | **扛支付网关回跳黑洞** | —（本方案最关键载体） |

**回跳黑洞**：跳转 ZipPay / GrabPay / Affirm 等第三方网关时离开本域，回跳到 callback `page.tsx`（Server Component）时，JS 内存态与部分 client storage 不可靠。**唯一稳定的载体是 Cookie**——因为：

* callback 是 **Server Component**（见 §9.2），Server 端只能读 Cookie，读不到 sessionStorage。
* 回跳 URL 的 query 由 provider 决定，不能塞自有 `traceId`。

Cookie 策略（草案，待安全/架构确认）：

| 属性 | 取值 | 理由 |
| --- | --- | --- |
| name | `cl_txn_trace`（待定） | 与现有 `X_CHECKOUT_TOKEN` 区分 |
| path | `/` | callback 路由可读 |
| domain | 当前站点域 | 回跳同域可读；跨子域按需放宽 |
| max-age | 单笔交易合理上限（如 30–60min） | 交易超时即应过期，不长期驻留 |
| SameSite | `Lax`（回跳为 top-level GET 导航，可带 cookie） | `Strict` 会在第三方回跳时丢失 |
| Secure | `true` | 仅 HTTPS |
| HttpOnly | **false**（前端要读写） | 若改为后端托管可设 true，见下 |

**决策点**：`traceId` 由**前端管理**（JS 读写 cookie，HttpOnly=false）还是**后端管理**（init checkout 响应 `Set-Cookie`，HttpOnly=true，前端从其它出口读）。前者改动小、可先落地；后者更安全、能 HttpOnly。建议先前端管理，迁移后评估收口到后端。

### 10.5 传播（跨系统 join）

* **下行（前端 → 后端）**：关键交易请求（create order / initiate / capture）带请求头 `x-txn-trace-id: <traceId>`，与现有 `X_CHECKOUT_TOKEN` 并存。BFF / 后端日志写入 Loki `txn_trace_id` 字段，实现前端报错 ↔ 后端订单/支付日志 join。
* **上行采集（后端 → 前端）**：每个交易 API 响应后读取响应头 `X-Request-Id`（即后端 OTel/Tempo trace），作为该步骤的 `trace_id` 记录，实现「前端步骤 → 后端 Tempo trace」弱关联（见 §10.8）。
* **回跳（网关 → callback page）**：靠 Cookie 还原 `traceId`（10.4），不依赖 provider query。
* **出口映射**：沿用 §5——Sentry tag `txn_trace_id`、Loki field `txn_trace_id`、Tempo `transaction.txn_trace_id`；**绝不进 metric label**（高基数，§5 铁律）。OTel 的技术 `trace_id` 另存一列，互不覆盖。

### 10.6 命名收口（业务 txn_trace_id vs OTel trace_id）—— ✅ 已确认方案 A

历史歧义：业务伞状 ID 与 OTel span trace 曾都映射到 Loki `trace_id`，语义不同会互相覆盖。**已确认采用方案 A**：

| ID | 来源 | 含义 | 出口命名（Sentry tag / Loki / Tempo） |
| --- | --- | --- | --- |
| 业务伞状 ID | 前端生成 | 贯穿整笔交易，跨页/跨回跳存活 | `txn_trace_id` / `txn_trace_id` / `transaction.txn_trace_id` |
| OTel 技术 trace | 后端生成，前端采集响应头 `X-Request-Id`（§10.8） | per-request，单 request 内 client↔server↔Tempo | `trace_id`（后端日志由 active span 注入） |

两 ID 在 Loki 同时存在、**互不覆盖、可联查**：用 `txn_trace_id` 回溯整笔交易，用 `trace_id` 钻取单次 request 的分布式 trace。

已回写 §5 映射表、§7 Loki 字段。`types.ts` 的 context 字段名保持 `traceId`（仅出口改名，无需改单一事实源）。被否方案 B（业务保 `trace_id`、OTel 改 `dd.trace_id`）不采用。

### 10.7 落地约束与分期

受 `AGENTS.md` § Observability Hard Rules **「Checkout / Payment / Cart: integration blocked」** 约束：

* **解封前可做（业务侧，不碰 Sentry capture）**：`traceId` 生成 / 幂等 / 持久化（sessionStorage + cookie）/ 回跳还原 / 请求头透传 / 步骤打点的数据结构。
* **解封后做（Sentry / OTel 侧）**：绑定 Sentry tag、写入 span attribute、错误关联。

### 10.8 前后端 trace 关联（现状 + 分期）

**现状（核对 2026-06-13，实测）**：

1. **后端已有 OTel/Tempo trace**：`order-api` 等服务每个 request 生成一个 32-hex trace（如 `ade497ca2f0772d52c92da706e5d3094`），写入 Loki 并 Links 跳转 Tempo。
2. **该 trace 通过响应头** `X-Request-Id` **回传前端**：前端拿到响应后即可读取（实测见请求详情 Response headers）。
3. `sentry-trace` **请求头未被后端关联**：前端请求时携带 `sentry-trace`，后端不消费、不 continue，因此前后端**未走标准分布式追踪**——后端每个 request 各开各的 trace。

**当前设计（已确认）：前端采集** `X-Request-Id`**，做弱关联。**

* 前端在每个交易 API 响应后读取 `X-Request-Id`，作为该步骤 context 的 `trace_id`（OTel 列）记录。
* `txn_trace_id`（per-transaction，前端生成）与 `trace_id`（per-request，源自 `X-Request-Id`）是**一对多**：一笔交易里挂多个后端 request 的 trace。
* 价值：从前端任一交易步骤 / 错误，可一键跳转到对应后端 request 的 Tempo trace；同时用 `txn_trace_id` 把这些散落的 request 串成整笔交易。
* 称「弱关联」的原因：不是同一条 OTel trace（无父子 span 关系），靠 ID 采集 + 字段 join，而非 trace 上下文自动传播。

**下一步推进方案（future，本期不做）：**`traceparent` **前后端真关联。**

* 走 W3C `traceparent`（或后端读取 `sentry-trace`）让后端 **continue** 前端发起的 trace，形成同一条端到端 OTel trace（父子 span）。
* 属后端排期 + 跨团队改动，留作后续目标；届时 `trace_id` 升级为「真·端到端 trace」，弱关联自然增强。

**对后端的两个请求（按成本从低到高）**：

1. **把前端** `x-txn-trace-id` **请求头透传进后端日志**（写入 Loki `txn_trace_id` 字段）——成本低，是 `txn_trace_id` 双向 join 的前提。
2. **读取** `traceparent` **/** `sentry-trace` **做 trace continue**——成本高，归入上面的下一步方案。
