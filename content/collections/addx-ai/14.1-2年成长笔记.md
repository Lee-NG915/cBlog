# 入职 A4x 后的 1—2 年：从 Shopify 执行者到 Web 业务 Owner

原文讲的是 AI 创业和 AI Native 组织。真正有用的不是「怎样用 AI 写更多代码」，而是：

> 当「把东西做出来」越来越容易，稀缺能力会转向理解用户、构建系统、治理债务、持续维护，并对最终结果负责。

Build 变快之后，维护、Review、权限、数据、文档、稳定性和协作边界会更早暴露。程序员不会消失，但一部分工作会从亲自生产代码，变成审阅、筛选、修改、整合，并对系统质量负责。

深圳部门只有我一个前端，日常是 Shopify 和运营支持。如果只把自己当成「接需求、改页面、上活动」，两年后还是页面开发经验。按上面这条思路，这份工作其实是完整训练场：真实业务、运营与转化、从前端规范到维护体系、对网站长期运行负责。

因此 1—2 年目标不是「把 Shopify 学熟」，而是：

> 从负责页面开发的前端，成长为能独立负责全球化电商 Web、建立工程体系、推动运营效率，并对长期质量和业务结果负责的高级前端。

前 12 周怎么融入，见 [入职培养方案](/addx-ai/onboarding)。本文管 1—2 年怎么长成 Owner。

---

## 五条主线

| 文章主线 | 原文问题 | 对我岗位的含义 |
| --- | --- | --- |
| Build 变快，债务也来得更快 | 上线后还有维护、数据、文档、权限、稳定性 | 「页面上线」不是需求结束 |
| 构建系统，而不是增加功能 | Task / 线性 Skill 替代不了可维护系统 | 不要永远手写活动页，要建设可复用能力 |
| 从「记者」变成「编辑」 | AI 能生成，人要判断、审阅、整合并兜底 | 审查、架构判断、验收和风险控制 |
| 通才并完成业务闭环 | 从用户问题一路到上线、数据和维护 | 不只还原设计稿，要懂运营目标和指标 |
| 信息差变小，实践差变大 | 看工具不等于有能力 | 必须用真实项目攒方法和案例 |

下面三条是日常工作原则；1—2 年路线在后文。

---

## 原则一：构建系统，不是堆功能

原文把工作分成 Task、Skill、系统。Skill 像线性 SOP；系统是网状的，要处理边界、权限、协作、回滚和质量检查。SEO 那个例子里：直接 Vibe Coding 最快但会失控；Markdown 把内容和代码分开，但对非技术同学不友好、改内容仍要 PR；成熟 CMS 把模板交给工程、把文案和 SEO 当数据，运营才能自助生产——但 CMS 不会自动保证内容质量和发布结果，仍要 Review。

翻译到运营说「下周要上一个海外促销页」：

| 层次 | 做法 | 结果 |
| --- | --- | --- |
| Task | 写一个页面上线 | 这次过了，下次重来 |
| Skill | 文案 → 素材 → 开发 → 埋点 → 测 → 发 | 更快，但仍绑在我身上 |
| System | 模板、Section/Block、字段、图约束、多语言、CTA、SEO、埋点、预览、发布记录、回滚、使用说明、复盘 | 运营配大部分内容，我做新能力和治理 |

入职后把高频需求分成三类：一次性的保证质量做完；会重复的抽成组件 / Section / 模板；跨页面、跨站点、要协作的，做成系统和流程。

每做完一个需求问一次：下次还会不会出现？如果会，怎样让下一次不用从头开始？

不要为了简历上 Headless。先用够 Shopify 自己的模板、Section、字段和运营能力。只有内容复杂、多渠道复用、交互受限或系统集成真成了瓶颈，再评估外部 CMS 或 Headless。成熟 SaaS 背后是稳定性、权限、容错和长期实践；能做 Demo 不代表该长期自研。要练 Build / Buy，不是「全部自己写」。

---

## 原则二：工作不是「上线」，是 Keep It Running

很多表面的增长问题，其实是基础设施：粗颗粒度的 GA 回答不了细漏斗；文档跟不上产品，客服和研发就会断层。AI 能加快写文档，跟不上变化一样没用。

Shopify 页面对我电脑上能看，不等于生产级。完整交付至少包括：多端多浏览器、多语言多地区、商品价格库存链接、SEO、事件、第三方脚本对性能的影响、运营会不会改、能不能回滚、上线后数据、文档和变更记录。

完成标准从「代码已经部署」改成：

> 已上线、经过验收、可以观测、能够回滚、有人维护，并且结果已经被复盘。

项目总结也不要只写「做了某个活动页」，要写清：为什么做、约束、如何可维护、稳定性、性能和数据、如何支持运营、上线结果、后续怎么养。

---

## 原则三：对质量负责的「编辑」，而不是写得最快的人

能运行的代码不是组织资产。能被别人理解、修改、复用和回滚的，才是。长期还要有变更上下文：业务原因、影响范围、数据、埋点、SEO、权限、老用户路径、回滚方式。

部门只有一个前端，我同时是主题维护者、运营页守门人、第三方脚本评估者、AI 代码 Reviewer、发布回滚负责人、性能 / SEO / 数据的排查人。要练的不只是写得快，还有：该不该做、改旧模块还是新开、有没有污染、第三方值不值得加、影响哪些页、AI 写得对不对、单测过了还有没有业务风险、以后的人能不能看懂。

AI 开发不要走「一句话 → 大改 → 能跑就上」。固定闭环：

1. 先写 Spec：目的、场景、验收
2. 限制可改文件和模块
3. 先 Review 计划，再让它改代码
4. 看 diff：无关修改、重复逻辑
5. 类型 / Lint / 构建 / 测试 / 主题检查
6. 用人体验和业务结果验收
7. 查性能、SEO、埋点、多语言、历史页
8. 更新文档：为什么改、改了什么
9. 上线后看真实环境
10. 复盘，把稳的做法收成组件、模板或规则

关注点从「AI 写了多少」改成：我能不能判断它对不对，以及我敢不敢对结果负责。

---

## 岗位四层，以及两年要到哪

不要把自己定义成「负责 Shopify，配合运营改页面」。升级成：

> 独立负责 Shopify 和相关 Web 的技术交付与长期治理：可复用主题、内容体系、发布流程、质量标准、数据体系和运营工具，并对体验、稳定性和业务效果负责。

| 层 | 含义 |
| --- | --- |
| 执行者 | 快速、准确地完成页面和功能 |
| 模块建设者 | 重复需求变成组件、Section、模板、工具 |
| 系统建设者 | 内容、发布、测试、监控、数据、文档、回滚成体系 |
| 业务 Owner | 理解目标、推动协作、做取舍，对上线结果和后续维护负责 |

1—2 年至少进入第三层，并开始具备第四层。

面对需求，不必变成专业运营 / 设计 / 后端，但要能判断：解决什么问题、面向谁、要提升点击还是购买、成功标准；用户从哪进、下一步做什么、信息层级和移动端；有没有模块可复用、一次性还是长期、要不要新数据、影响哪些页、怎么测和回滚；记哪些行为、上线后怎么看效果、运营以后能不能改、文档归谁。

## 1—2 年路线

### 0—3 个月：看清系统，不要急着大改

细节清单跟 [入职培养方案](/addx-ai/onboarding) 对齐。这一阶段的成果是：网站资产地图、主题架构、第三方依赖、运营需求分类、性能与质量基线、技术债优先级、发布和回滚说明。

不要为了展示能力立刻重构。先理解系统为什么长成这样，再挑第一批值得治理的问题。

### 3—6 个月：从接单变成可复用交付

建设：Section / Block 规范、Snippet 与组件边界、模板和字段命名、Git 与审查、预览和上线清单、变更与回滚、运营使用说明、AI 代码审查。

成果：一套活动页模块、一套商品或内容模块、页面开发约定、运营能用的模板、PR 模板、上线清单、故障回滚 SOP。

衡量标准不是做了多少页，而是：过去必须找前端的重复工作，有多少已经能靠系统解决。

### 6—12 个月：性能、数据、长期维护

* **性能**：核心页基线、图片字体视频和第三方脚本、性能预算、优化前后对比
* **数据**：核心漏斗、事件命名和字段、避免重复统计和口径混乱、上线复盘
* **稳定性**：错误监控、404 和失效资源、关键流程跨设备、重大需求回滚方案
* **文档**：组件说明、变更记录、字段变化同步、故障排查路径

至少留下一个带上线前后数据的完整案例。

### 12—18 个月：主导一次真闭环

选一个能从头跟到维护的项目，例如：多语言 / 多市场、内容与运营管理、PDP 或购物车转化、SEO 内容系统、运营页工具、埋点治理、第三方集成、Node / GraphQL / Webhook 自动化。

要同时证明：业务分析、需求拆解、选型、架构、实现、数据与测试、协作、发布回滚、复盘、长期维护。不是证明「我会开发」。

### 18—24 个月：变成可验证的案例

至少三个方向，数字从入职第一天记，不要跳槽前编：

1. **运营平台化**：高频问题 → 模块和内容模型 → 运营自助 → 发布流程 → 效率结果
2. **性能和稳定性**：原始指标 → 定位 → 方案 → 兼容回滚 → 上线结果 → 长期监控
3. **数据和业务闭环**：漏斗 → 事件治理 → 页面或流程优化 → 实验 → 转化 → 迭代

Shopify 是业务场景，不是技术边界。同时补大公司常考的基础：JS / TS、浏览器和网络、React、工程化、性能、测试、Node、系统设计、算法。

## 每个需求同一套问题

1. **为什么做**：用户问题、业务目标、怎样算成功
2. **做成什么**：一次性页 / 可复用模块 / 运营配置 / 自动化 / 长期系统
3. **会影响什么**：其他页、数据、SEO、性能、多语言、历史内容、第三方
4. **怎样保证质量**：验收、自动检查、人工测、发布、监控、回滚
5. **怎样长期维护**：内容归谁、代码归谁、文档在哪、要不要 Review、怎么排查、下次能否复用
6. **能沉淀什么**：组件、模板、工具、规范、文档、数据结论、案例

---

## 要避开的状态

* 每天很忙，全是一次性改页，没有系统
* 把 AI 生成速度当成工程能力
* 为技术而推 Headless
* 只关注上线，没有数据、监控和复盘
* 因为只有一个前端就省略流程——一个人更需要规范、文档和回滚
* 什么都自己写，把 Demo 能力当成长期自研理由

不理想的两年后表述：

> 负责 Shopify 网站开发，根据运营需求完成活动页和日常维护。

更接近目标的表述：

> 独立负责 Shopify 与 Web 的技术交付和长期治理，建立可复用主题模块、内容配置、发布与回滚，并推动高频运营需求自助化。

> 主导核心页性能、SEO 和稳定性，建立关键路径的事件规范与上线复盘，用可量化指标优化体验和转化。

> 基于真实运营问题做内部自动化和系统集成，负责从需求分析到上线监控和后续维护的完整闭环。

---

## 收束

单前端、自主性大，既是机会也是风险。机会是能碰完整业务、自己建体系；风险是两年后仍只有改页面的履历。

要主动完成三次转变：从完成页面到解决业务问题；从增加功能到构建可维护系统；从亲自写代码，到能判断、审阅、整合并对最终质量负责。

信息差会越来越小，实践差会越来越大。未来两年最重要的方法不是收藏更多文章，而是：

> 选择真实问题，完成完整闭环，留下系统成果，并用数据证明价值。
