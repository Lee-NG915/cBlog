# 入职培养方案：把上一份三个月计划套到 addx.ai

来源是上一份工作的「新人培训计划表」结构，不是那家公司的流程复印件。我拿它当 **入职后 3 个月自学与对齐框架**：先融入、再补缺口、再独立交付。

总体目标沿用原表：熟悉环境和职责，补齐语言与框架短板，逐渐融入团队；培养主动性、执行力、学习能力、自主解决问题能力，最终能独立完成业务需求。

时间按 **入职日 = Week 0 / Day 1** 起算，约 12 周。具体日期入职后填。伙伴 / 直属上级入职当天问清楚，不要自己猜。

入职第一周必须当面确认的岗位边界（来自 [面试准备总览](/addx-ai/overview)）：

- 主要做 Shopify Theme，还是 Hydrogen / React Headless？
- 一个品牌站还是多品牌、多市场？
- 后端是 Shopify App / Webhook，还是已有 Java / Node 服务？
- 是否负责支付、物流、订阅应用集成？
- 性能以 CrUX、Lighthouse 还是内部 RUM 为准？
- 有没有 on-call，订单和支付事故归谁？

未确认前，下面「业务系统」一列按 **官网 / 用户 Web / 订阅与硬件电商入口** 来学，不要把 Shopify 细节说成已核实事实。

## 第一阶段：职责、组织、流程、规范

目标：知道自己在团队里干什么、需求从哪来、代码怎么上线。

| 主事项 | 内容 | 时间 | 目标及输出 | 备注 |
| --- | --- | --- | --- | --- |
| 入职准备 | 工位与账号；常用软件；团队成员与仓库范围；权限申请 | Day 1 | 本地能 clone 主仓库；能打开需求板、文档、CI、监控；列出缺的权限 | 权限清单当天发给上级，不要默默等 |
| 团队介绍 | 职责、业务范围、成员、工作流程、日常方法、部门结构 | Week 1（约 5 个工作日） | 一页笔记：谁负责官网 / App Web / 订阅 / 增长；需求怎么提、怎么验收、怎么发版；本地跑通一个可预览站点 | 输出给自己看，不求完美 |
| 基础技术 | HTML / JS / CSS；JavaScript、React、Next.js；Node 基础；组件库或设计系统入门；Sentry / Datadog 或团队现用观测；GitHub Actions 或现用 CI/CD | Week 2（约 5 个工作日） | 能按仓库规范改一个小页面并走通预览；知道错误打到哪、日志怎么查 | 系统化过一遍即可。八股见 [07](/addx-ai/07)，观测见 [03](/addx-ai/03) |
| 业务学习 | 验证、测试、发布流程；需求工具怎么改状态；编码与文档规范；产品主链路 | Week 2 后半（约 3 个工作日） | 能按需求票从开发到自测描述一遍；画出「硬件 → 云 / AI → App/Web → 订阅或电商变现」；列出用到的第三方（支付、邮件、分析、CMS、Shopify 应用等） | 第三方以仓库和文档为准，入职后再填真实名单 |

业务主链路先按这个理解，入职后用真实产品名替换：

`视觉硬件采集 → 云端或边缘推理 → App / Web 展示 → AI 订阅或硬件电商变现`

Web 侧很可能承接品牌展示、硬件销售、用户转化、全球化和订阅入口，而不是孤立官网。

## 第二阶段：规范、工具、业务体系、技术框架

目标：为独立改需求做储备，不要求这一周就上大功能。

| 主事项 | 内容 | 时间 | 目标及输出 | 备注 |
| --- | --- | --- | --- | --- |
| 熟悉业务 | 官网与多语言站；用户 Web；订阅 / 增值；硬件电商或 Shopify 店（若属实）；CMS / 运营配置；内部运营后台 | Week 3（约 4 个工作日） | 表：项目 / 仓库 / 谁负责 / 怎么验证 / 怎么发布 / 注意事项；主要模块清单；1～2 条核心用户路径流程图（浏览 → 转化 → 支付或订阅 → 回看或履约） | 路径以真实产品为准：VicoHome、Vico Nature、官网、店铺 |
| 专业技能（进阶） | 现用渲染方案（App Router / Theme / Headless）；状态与数据获取；设计系统与组件规范；前后端边界（BFF、App Proxy、Webhook） | Week 3–4（约 5 个工作日） | 能讲清：页面数据从哪来、缓存在哪、发布怎么走、组件在哪扩展；画一张「浏览器 → Web → Shopify 或自有 API → Webhook / 任务」 | Shopify 未确认前，先学官方 Theme / Hydrogen / Webhook 模型，对照仓库验证。缺口见总览 §3 |

进阶对照（入职后用仓库替换）：

- 站点：多语言、多市场、SEO、Core Web Vitals
- 组件：可复用模块，而不是每个活动页从零写
- 服务端：Node 路由、Webhook 去重、少量持久化、定时任务
- 观测：错误、发布回归、订阅或下单成功率，不要只看页面 exception 数

已有可迁移经验：Monorepo 域分层、设计系统 / CDD、ISR 与缓存、交易鉴权、Sentry + Grafana。缺的是 **Shopify 平台模型** 和 **独立后端服务的完整 ownership**。入职后用真实仓库把这两块补成「能讲、能改、能上」。

## 第三阶段：用真实需求走完流程

| 主事项 | 内容 | 时间 | 目标及输出 | 备注 |
| --- | --- | --- | --- | --- |
| 实际项目 | 接 1～2 个中小需求，自己走完计划 → 开发 → 沟通 → 确认 → 自测 → 预览 / 提测 / 发布 | Week 5–8 | 质量合格的上线或预发产出；一份「这个需求实际怎么走」的流程笔记 | 主动找产品、设计、后端对齐，不要只在票里等 |

质量标准沿用原表：产出达到团队标准；能独立说清范围、风险、验证方式和回滚。

优先挑能暴露全栈边界的需求，例如：

- 营销页或商品模块，带多语言和性能约束
- 订阅或下单相关展示，带 Webhook / 状态回写
- 一次真实的发布回归：看错误量、核心转化、缓存是否脏

## 第四阶段：个人业务目标

原表这一阶段写的是设计系统一致性、CDD、组件测试覆盖。那是上一份工作的目标，**不要原样带到新团队当承诺**。

在 addx.ai 的三个月个人目标改成：

> 通过独立交付 1 条 Web 业务链路（页面模块 + 必要的服务端 / Webhook + 发布验证），把全球站的一致性、性能和交付效率做成可重复的工作方式，而不是单次改页面。

建议输出（和上级对齐后改）：

| 输出 | 说明 |
| --- | --- |
| 站点与模块地图 | 官网 / 用户 Web / 店铺（若有）各模块、责任人、发布方式 |
| 一条可复用交付路径 | 需求 → 组件或 Theme 模块 → 预览 → 观测 → 上线 |
| 性能基线 | 关键页 LCP / INP 或团队指定指标，发布前后可对比 |
| 全栈闭环笔记 | 一次 Webhook 或订阅 / 订单状态如何从第三方回到页面 |

原表里「推动 CDD、补组件测试」仍然有用，但要等看过现有组件库再提，避免一入职就推销上一份工作的方法论。

## 第五阶段：总结

| 主事项 | 内容 | 时间 | 目标及输出 | 备注 |
| --- | --- | --- | --- | --- |
| 总结及答辩 | 工作总结、文档整理 | Week 12 前后 | 培训期间事项清单；学习笔记；遇到的问题和解法；给团队流程的 1～3 条具体建议 | 月中可以先做一次短汇报 |
| 学习成果汇报 | 月总结 | 每月末 | 当月交付、缺口、下月计划 | 对上级透明，不堆流水账 |

评估标准沿用原表：能说清这三个月做了什么；笔记别人能看懂；能指出流程里真实摩擦，而不是空泛吐槽。

## 入职后立刻要问的清单

1. 主仓库、预览环境和谁有 merge 权。
2. 需求工具、文档空间、值班群。
3. 错误与日志平台（Sentry / 云日志 / 自建）。
4. 生产发布是 GitHub Actions、店铺发布，还是另有流水线。
5. 密钥和第三方后台怎么申请（Shopify、支付、分析、CMS）。
6. 第一个适合新人的需求是哪张票。

公司与产品背景：[公司研究](/addx-ai/company-research)。面试期缺口：[复习索引](/addx-ai/index)。入职后以仓库和同事口径覆盖这些笔记。
