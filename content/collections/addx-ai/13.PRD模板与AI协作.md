# PRD 模板与 AI 协作

1. **为什么是这套章节**：大厂方法 + AI 模板对比后的取舍。
2. **可填写模板**：评审到上线共用一份。
3. **给 AI 的 prompt**：先追问，再按同一结构出稿。

用法：自己写就从「可填写模板」起；和 AI 一起写，就把第三部分整段复制过去。

---

## 一、调研：大厂怎么拆 PRD，这套模板怎么来的

### 1. 调研对象

- 公司/组织方法：AWS、Amazon、Google、Microsoft，以及上一份工作里的组件型电商 PRD
- AI 协作模板：`prd-taskmaster`、`vibecoding`

### 2. 各对象在划分什么

#### AWS

- **Product vision / Start with why**：做这件事的价值和方向。
- **Success metrics**：成功标准。
- **Business case**：投入产出与优先级。
- **Delivery plan**：特性和节奏变成可执行发布计划。

参考：

- [AWS Prescriptive Guidance: Strategy product development](https://docs.aws.amazon.com/prescriptive-guidance/latest/strategy-product-development/introduction.html)
- [AWS: Start with why](https://docs.aws.amazon.com/prescriptive-guidance/latest/strategy-product-development/start-with-why.html)

#### Amazon（Working Backwards）

- **PR（Press Release）**：先用面向客户的语言定义价值主张。
- **External FAQ**：客户/市场问题。
- **Internal FAQ**：技术、法务、运营等内部问题。
- **Backward planning**：从目标体验倒推实现路径。

参考：[Working Backwards PR/FAQ](https://www.workingbackwards.com/resources/working-backwards-pr-faq)

#### Google（公开工程实践可借鉴部分）

- **PRD（What/Why）**：做什么、为什么做、成功标准。
- **Design Doc（How）**：如何实现、技术权衡和风险。
- **Review practice**：用文档评审提前发现问题。
- **Open questions / trade-offs**：显式记录未决问题和取舍。

参考：[Google Engineering Practices](https://google.github.io/eng-practices/)

#### Microsoft（Functional Specification）

- **Requirement IDs**：需求编号，支持追溯。
- **Functional Specification**：交付基线，明确行为与约束。
- **Traceability**：需求到功能、测试、发布可追踪。
- **Baseline / change control**：评审通过后按变更流程管理。

参考：[Microsoft Learn: Write the Functional Specification](<https://learn.microsoft.com/en-us/previous-versions/tn-archive/cc543349(v=technet.10)?redirectedfrom=MSDN>)

#### 组件型电商 PRD（上一份工作实践）

- **Component Basic Information**：组件边界、依赖与上下文。
- **UI/UX + Interaction**：页面行为、状态与交互反馈。
- **Fields Description**：字段、类型、限制、数据来源。
- **Tracking + Go-live Checklist**：埋点与上线检查项。

适合「需求已经清楚、要快速交接实现和上线」的组件交付，不适合当价值决策文档。

#### `prd-taskmaster`

- **多轮澄清（Q&A）**：先补齐信息再生成文档。
- **结构化 PRD 生成**：需求转固定结构。
- **质量校验**：完整性、可测试性、清晰度。
- **任务拆解联动**：PRD 映射到执行任务。

参考：[GitHub: anombyte93/prd-taskmaster](https://github.com/anombyte93/prd-taskmaster)

#### `vibecoding`

- **意图到规格转译**：模糊想法变成可执行描述。
- **跨角色协作语义**：统一产品、设计、工程语言。
- **知识库式组织**：PRD 作为体系的一部分。
- **流程化协作**：从探索到交付连续协作。

参考：[GitHub: cpjet64/vibecoding](https://github.com/cpjet64/vibecoding)

### 3. 洞察

共性：

- 都在把「业务意图」转成「组织可执行协议」。
- 主线都是：价值（Why）→ 范围（What）→ 落地（How/Delivery）→ 验证（Success/Acceptance）。
- 都在平衡用户价值、交付成本、组织风险。
- 文档要能支持决策、评审、上线和复盘，不是写完就算。

差异：

- **阶段**：AWS、Amazon 更适合方向和价值还不确定；Google、Microsoft 更适合复杂实现和风险控制；组件型电商 PRD 更适合明确需求后的高效交付；AI 模板更适合从澄清到任务化。
- **组织**：跨团队依赖多，需要 Microsoft/Google 的可追溯和分层评审；团队小、节奏快，更依赖执行模板和 AI 提速。
- **风险**：价值风险用 Amazon/AWS；交付风险用 Google/Microsoft；执行遗漏用组件型交接清单；信息不完整用 `prd-taskmaster` / `vibecoding`。
- **治理**：Amazon/AWS 偏对齐与决策；Google/Microsoft 偏控制与审计；组件型 PRD 偏交接与上线；AI 模板偏生成与编排。

结论：没有单一最佳模板。组合使用——先用价值叙事定方向，再用规格/验收固化边界，最后用执行模板和 AI 提高交付效率。

落地建议：

- 三层文档：L1 价值决策（Why/目标/ROI），L2 需求规格（范围/规则/验收），L3 交付执行（任务/上线/复盘）。
- 先定成败标准再写功能。
- 把范围管理写成机制：non-goal、变更入口、审批人、版本冻结点。
- 验收前移：场景、规则、可测试口径必须一起有。
- 模板是工具，不是目标。

### 4. 横向对比

| 对象             | 总结归类     | 核心概念划分                                                      | 这些概念主要做什么                   | 对比结论                   |
| ---------------- | ------------ | ----------------------------------------------------------------- | ------------------------------------ | -------------------------- |
| AWS              | 策略导向     | Vision / Metrics / Business case / Delivery                       | 先定义方向与成功，再落到优先级和交付 | 适合先定方向与资源投入     |
| Amazon           | 策略导向     | PR / External FAQ / Internal FAQ / Backward planning              | 先讲客户价值，再回答内外部关键问题   | 适合价值不清晰阶段做对齐   |
| Google           | 工程治理导向 | PRD（What/Why）/ Design Doc（How）/ Review / Open questions       | 通过产品与技术分层降低返工并暴露风险 | 适合复杂协作中的分层治理   |
| Microsoft        | 工程治理导向 | Requirement IDs / Functional Spec / Traceability / Change control | 把需求变成交付基线并可追踪、可控变更 | 适合高风险、强流程项目     |
| 组件型电商 PRD   | 执行落地导向 | Component info / UIUX+Interaction / Fields / Tracking+Go-live     | 面向组件交付，强调实现细节和上线执行 | 适合强执行、强交付场景     |
| `prd-taskmaster` | AI 协作导向  | 多轮澄清 / 结构化生成 / 质量校验 / 任务联动                       | 先补齐信息，再稳定产出并连接执行任务 | 适合 AI 驱动的任务化推进   |
| `vibecoding`     | AI 协作导向  | 意图转译 / 协作语义统一 / 知识库组织 / 流程化协作                 | 把抽象需求转为可协作、可沉淀内容     | 适合探索期到协作期连续推进 |

### 5. 这套模板的设计思路

设计目标：

- **先决策后执行**：先 Why/目标/范围，再流程、规则、验收。
- **一份文档覆盖评审到上线**：产品、研发、测试、运营共用，减少口径漂移。
- **控制复杂度**：核心章固定，按需章可选。
- **可验证**：每章都能落到场景、规则、验收、上线检查。

| 模板章节                     | 设计意图                       | 解决的问题                       | 输出标准                               |
| ---------------------------- | ------------------------------ | -------------------------------- | -------------------------------------- |
| `元信息`                     | 协作上下文和版本基线           | 负责人不清、状态不清、版本难追溯 | 负责人、状态、版本、关联文档可直接查   |
| `一、背景与目标`             | 固化业务价值与边界             | 为什么做不清、范围蔓延           | 背景、目标、非目标可被复述             |
| `二、业务流程与场景`         | 用场景驱动需求表达             | 需求碎片化、跨团队理解不一致     | 每个场景包含状态、操作、反馈、数据变化 |
| `三、规则与口径`             | 把歧义前置消解                 | 评审通过后仍频繁追问定义         | 规则清单、关键定义、边界说明完整       |
| `四、交互与体验说明（按需）` | 对复杂交互做集中约束           | 交互复杂但分散在文本里难执行     | 页面/模块、状态、体验要求可核对        |
| `五、验收与上线说明`         | 从「写需求」过渡到「交付结果」 | 验收口径不一、上线前漏项         | 验收表+上线检查单可直接执行            |
| `六、参考资料（可选）`       | 连接上下游信息源               | 深挖资料分散、追溯成本高         | 设计/技术/历史文档有明确入口           |

取舍：

- 技术实现不写进主 PRD，放技术方案。
- 交互章节按需启用，简单需求不单独开章。
- 结构标准化，内容业务化，不强迫填满。
- 优先可执行：每一章都要能指导下一个角色干活。

## 三、给 AI 的 Prompt（整段复制）

> **使用方式**
>
> 1. **将本段整体复制给 AI。**
> 2. **先填写你已经知道的信息，不知道的留空即可。**
> 3. **AI 需要先通过多轮问答帮你梳理需求，再输出最终 PRD。**
> 4. **如果信息不足，AI 应继续追问或标记“待确认”，不要擅自编造。**

### 你的角色

你是一位高级产品经理，负责协助用户梳理需求，并最终生成一份简单易懂、详细清晰、专业但不复杂的 PRD。

你的目标不是立刻生成一份看起来完整的文档，而是先帮助用户把需求想清楚，再输出最终 PRD。

### 你的工作方式

请严格按以下步骤进行：

#### 第一步：先理解，不要急着生成

- 先阅读用户提供的信息。
- 判断当前信息是否足够生成 PRD。
- 如果信息不足，不要直接生成文档，先提问。

#### 第二步：多轮追问，补齐关键缺口

优先确认以下问题：

1. 这次需求要解决什么问题？
2. 谁是目标用户？
3. 用户的主流程是什么？
4. 这次具体要做哪些能力？
5. 本期明确不做什么？
6. 有哪些关键场景和异常场景？
7. 哪些规则会影响产品行为、研发实现或测试验收？
8. 是否存在需要单独说明的页面、模块、状态、反馈或设计约束？
9. 有没有容易引起歧义的定义需要说明？
10. 上线前至少要确认哪些事情？

如果用户回答得不清楚，请继续追问，直到核心信息足够完整。

#### 第三步：帮用户收敛，而不是发散

- 不要为了显得专业而堆很多形式化章节。
- 不要把 PRD 写成技术方案、接口文档或测试用例库。
- 不要引入用户没有明确需要的大量治理内容。
- 如果某些内容可以轻量说明，就不要展开成大章节。
- 如果交互不复杂，就把 UI/UX 内容放在场景里；只有页面、状态或交互明显复杂时，才单独输出“交互与体验说明”。

#### 第四步：输出最终 PRD

在信息足够后，输出一份结构清晰、可直接使用的 PRD。

如果仍有少量未确定内容：

- 在文档中明确标记为“待确认”
- 不要自行补全假设内容

### 输出要求

最终 PRD 请严格采用以下结构：

#### 1. 背景与目标

需要包含：

- 背景：当前现状、问题或缺口
- 本期目标：本期要交付什么
- 本期不做：本期明确排除哪些内容
- 补充说明（按需）：指标说明、责任边界、合规说明、沿用规则等

#### 2. 业务流程与场景

需要包含：

- 整体流程：按时间顺序写清楚主链路
- 关键场景：至少覆盖最核心的业务场景
- 异常场景：只写关键异常，不要把所有系统异常都写满

每个关键场景尽量写清：

- 用户状态
- 用户操作
- 预期结果
- 数据状态变化

#### 3. 规则与口径

需要包含：

- 业务规则
- 关键定义
- 边界与说明

重点是让读者遇到问题时，能在这一章快速查到答案。

#### 4. 交互与体验说明（按需）

只有在以下情况下才输出本章：

- 页面或模块较多
- 状态切换较多
- 交互反馈对需求理解很重要
- 需要明确空态、错误态、成功态或设计稿引用

如果交互不复杂，请不要单独输出本章，而是把相关内容写进“业务流程与场景”。

#### 5. 验收与上线说明

需要包含：

- 验收要点：主场景和关键异常场景如何判断通过
- 上线说明：上线前必须确认哪些事项

### 风格要求

请严格遵守以下风格：

- 用中文简体输出
- 用产品语言，不要堆技术术语
- 简单易懂，让第一次看的人也能快速理解
- 专业、有职业素养，但不要形式主义
- 一件事只写一处，避免重复
- 先讲流程，再讲规则，再讲验收
- UI/UX 内容优先跟场景走，只有复杂时才单独成章
- 如果某章节不适用，可以省略
- 如果某项不需要展开，也要简单说明原因

### 不要这样做

- 不要一上来直接生成完整 PRD
- 不要虚构背景、规则、指标、异常处理方式
- 不要堆大量编号、缩写、测试语法
- 不要把幂等键、并发锁、表结构、错误码矩阵写进主文
- 不要为了显得完整而加入很多无价值章节
- 不要机械输出“交互与体验说明”章节，除非确实需要
